# Design

## Who runs cleanup after the session is gone

The cleanup tool already has everything it needs to remove a merged worktree safely; what it lacks is an invocation. Three triggers were considered. Keeping the delivering session alive until merge blocks the agent and fails whenever the session is closed first. A background `watch` process reacts within minutes but requires the maintainer to start and keep a local process, which the local-cleanup specification deliberately leaves optional. The chosen trigger is the next agent session: agents create worktrees at session start, in the primary checkout, with GitHub access already available, so that moment is the natural point to reconcile earlier deliveries. Cleanup therefore happens on the first session after merge rather than at merge time, which is what the maintainer experiences as "no leftovers" without any process on the machine. A session that is alive when the maintainer reports a merge still cleans up immediately through the same sweep.

## Authority model

The existing rule is that registration never authorizes deletion; the owner's explicit release does, and the exact-candidate `complete` invocation after verified merge is that release. With hand-off the release moves earlier: the owning agent releases the candidate when it stops using it, which is exactly what the "Automatic authority is explicitly registered and released" requirement already asks for. The release carries no timing claim; it says "when this PR is verified merged and archived and its remote ref is gone, this worktree and its topic ref are mine to remove". The sweep exercises that authority per candidate, after re-verifying the gates on every pass, and nothing else: it never adopts a folder or branch that was not handed off (except the branch-pruning rule below, which has its own evidence), never discards a closed-unmerged candidate, and never enables the persistent queue. `handoff` and `sweep` are both explicit invocations, so a disabled queue does not block them, but a stop sentinel written while a sweep runs still halts it before the next destructive step, because that sentinel is the maintainer's emergency stop for any local mutation.

Hand-off happens with the candidate pushed and the worktree idle. Tracked, staged, unstaged, or untracked content at hand-off is a sign of unpushed work, so `handoff` blocks with the affected paths instead of releasing; the central disposable roots are exempt as they are at removal. A repair after hand-off follows the existing rule: the session claims the registration, repairs and repushes, then hands off again, which updates the recorded head and releases again. Because `handoff` is idempotent per exact worktree, repeated invocations never create a second registration.

## Finalization ancestry

`complete` compares the registered head with the merged PR head and fails closed on any difference. Since #456 the finalization App pushes its commit onto the branch after the agent's last push, so the registered head is one commit behind the merged head on every version-3 delivery, and today's reports for #457 and #458 block on `candidate-head-association`. The equality was a proxy for "this checkout holds nothing that was not accepted". The precise form of that statement is ancestry: if the registered head, the live worktree HEAD, and the local topic-ref tip are each equal to or an ancestor of the merged PR head, every commit reachable from them is reachable from a head that the maintainer accepted and merged, and deleting the checkout and ref loses nothing. Ancestry is checked with GitHub's compare API (`base...head` must be `ahead` or `identical` with the tip as merge base), which the evidence reader already uses and which keeps the evidence module free of local Git; a commit GitHub does not know is by definition unaccepted. Any tip holding a commit outside the merged head therefore blocks, so a local commit made after hand-off is preserved. Comparing against `origin/develop` instead would not work: the repository squash-merges, so PR commits are never ancestors of `develop`. The branch attachment stays exact; a worktree whose branch changed is still identity drift.

Ref deletion changes accordingly. The compare-and-delete reads the tip immediately before deletion, requires it to be equal to or an ancestor of the merged head, and deletes with that exact tip as the expected old value; the journaled head is no longer the only accepted value, but the deletion is still atomic against concurrent movement.

## Sweep

`sweep` reuses the queue's evaluation loop and its limits (100 registrations, 500 remote requests, 10-second subprocess deadline, durable round-robin cursor) with two differences: its elapsed-time budget is 180 seconds rather than 60, because each merged candidate costs three evidence loads of roughly six seconds each and the first live run hit the 60-second deadline after two candidates; and it requires no prior `enable`, because its authority is each candidate's hand-off release rather than the maintainer's queue permission. For each released entry it runs the same reconciler as `complete`. Outcomes are the existing dispositions plus `awaiting-discard` for a closed-unmerged PR, which is reported so the agent can relay it and never acted on. Coverage that runs out is reported as deferred and resumes on the next sweep. Two sessions sweeping concurrently share the existing mutation lock; the loser reports `deferred` rather than waiting, so a new session's start is never held by another session's cleanup. The sweep prints one line per candidate suitable for relaying in the agent's first reply.

## Evidence-based branch pruning

A local branch differs from a folder: it holds no uncommitted content, and if its every commit is reachable from a merged PR head it holds nothing unique. That is why the sweep may prune branches it never registered while still refusing to adopt folders. The evidence per branch is: the name follows `type/short-description` and is not `develop` or another protected or reserved name; no worktree has it checked out; no live registration names it (a registered branch is handled by its candidate); exactly the GitHub lookup for pull requests with that head ref name in this repository returns at least one merged PR into `develop` and no open PR; the tip equals or is an ancestor of the most recent such merged PR's head; and the remote ref `refs/heads/<name>` is absent on `origin`. Deletion is compare-and-delete with the tip read immediately before. Anything else is reported with a reason (`branch-no-pull-request`, `branch-open-pull-request`, `branch-unmerged-commits`, `branch-checked-out`, `branch-remote-present`) and retained. The sweep may run one prune fetch of `origin` first so that stale remote-tracking refs disappear with the branch; that fetch touches no local branch or worktree.

## Evidence cost

Profiling one live verification of #458 showed 47 sequential GitHub requests, 30 of them blob reads by SHA, at roughly 250 ms each; a legacy version-2 candidate needed 76. The reconciler verifies a candidate three times (evaluation, before removal, before ref deletion), so one version-3 candidate cost about 36 seconds and the first live sweep hit the 60-second deadline after two candidates. The reader now memoizes SHA-addressed objects for its own lifetime, one pass: `git/blobs/<sha>`, `git/trees/<sha>`, `git/commits/<sha>`, and `compare/<sha>...<sha>` cannot change under their SHA, so reusing them across revalidations weakens nothing; pull-request, ref, run, and timeline state is always refetched. The cache is bounded to 1000 entries and 64 MiB. Measured again, #458 costs 24 requests on the first verification and 9 on each later one (7.6 s, then 3.5 s), and the live sweep completed four candidates plus branch pruning in 55 seconds.

## Stale mutation lock

The mutation lock is a `wx`-created file removed in a `finally`. A process killed by a tool timeout or a closed terminal never runs that `finally`, and this morning's lock (PID 38204, no such process) blocked every later `complete` with `mutation-busy` until it was deleted by hand. The runbook forbade automatic eviction because a PID alone cannot distinguish a slow holder from a dead one. The lock now carries a heartbeat that the holder rewrites every five seconds while it runs. Eviction requires both signals: no heartbeat for two minutes (a legacy lock without one is judged by its modification time) and a PID that `process.kill(pid, 0)` reports as absent. Each failure mode errs toward keeping the lock: a reused PID reads as alive, a PID the caller may not signal reads as alive, and a fresh or unreadable-but-fresh file is busy. An eviction is written as `lock-evicted-<time>-<id>.json` beside `state.json` with the evicted record, and it releases no ownership and advances no journal; the entries' own journal steps still govern what the next mutation may resume.

## What this is measured by

After merge and one `sweep` from the primary checkout, the released entries for #457 and #458 should report `removed` (or `already-absent` for a hand-deleted folder) with `local-ref-removed`, no `released` entry should remain for a merged PR, and `git branch` should list only `develop`. A subsequent delivery that ends with `handoff` and is later merged should be removed by the next session's opening sweep with no command typed by the maintainer. A branch carrying one local commit after hand-off should survive every sweep with `branch-unmerged-commits`.
