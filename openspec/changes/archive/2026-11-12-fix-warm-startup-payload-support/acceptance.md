# Conditional implementation acceptance

Verdict: accepted only when an authorized human directly merges the containing exact pull-request head after required current-head validation, explicitly asks the active agent to execute that protected exact-head merge while it is currently eligible, or personally enables native auto-merge for the unchanged head and GitHub integrates it after validation succeeds.

The maintainer integration decision accepts these scenarios:
- Compatible selected releases accept invocation color and literal prompts on cold and repeated compact warm launches.
- Startup capability evidence is authenticated and bound to the exact selected release, never borrowed from another installed or retained candidate.
- Unsupported or unverifiable selected releases fail before their UI spawn without silently dropping or retrying without the payload.
- Update fallback, activation races, and bounded reselection independently enforce support for the ultimately selected release.
- Existing restart seals remain compatible, and no-payload launches add no capability-resolution manifest reads or payload rehash.
- First visible trust and editor presentation uses invocation color without saved-settings writes; live control, peer isolation, replacement, discovery, and comparison behavior remain unchanged.
