# Design

## Where compaction progress can be measured

Pinned Pi compacts with one summarization request (two for a split turn) sent through the session agent's public `streamFunction`; the session reads only the final result of that stream, and the stream itself is never iterated by Pi. Pi emits `compaction_start` and `compaction_end` and nothing in between, so the adapter has no event to derive progress from. The agent's stream function is a public, assignable field that Pi's own SDK sets at construction, and Pi reads it at call time for every request. The adapter therefore wraps it once per bound session: the wrapper calls the original, and between `compaction_start` and `compaction_end` (no other request is in flight then, because compaction runs between turns or after aborting the run) it additionally iterates the returned stream in the background, counting the characters of each `text_delta`, and returns the same stream object untouched. Outside compaction the wrapper is a pass-through and iterates nothing, so ordinary agent runs and branch summaries see exactly the stream they would have seen. The wrapper is installed only when the field is a function, is removed when the session is unbound, and its absence degrades to the current `Compacting...` label; this is the explicit optional-capability shape the Pi boundary requires rather than a silent probe.

## How the percent is estimated

The summary's final length is unknown while it streams, and the request's token ceiling is far above any real summary, so progress is measured against an expected summary size instead. When the current branch already holds a compaction entry, its summary length is the expectation: Pi's update prompt merges the previous summary with the new material, and consecutive summaries in one session are close in size. For a first compaction a fixed default of 4,000 characters is used. The percent is `floor(100 × streamed / expected)` clamped to at most 99 while compaction is running, so the label never claims completion before `compaction_end`; a summary longer than expected holds at 99 rather than overshooting. The count accumulates across a split turn's second request and across a retried request within the same compaction, and resets at `compaction_start`. The adapter publishes a new percent only when the integer changes, so a compaction produces at most one hundred status events, and `compaction_end` clears it together with the compacting state.

## How the percent reaches the screen

The status view gains an optional `workingProgress` percent beside `workingMessage`; producers keep supplying the semantic word `Compacting` and never bake punctuation or numbers into it, preserving the existing presentation-boundary rule. The bare-A1 status presenter composes `Compacting (37%)` and hands it to the shared spinner rule, which appends the canonical `...`. The `a1 pi` comparison route ignores the percent and keeps `Compacting...`, the same gating the pending-steering presentation already uses. Because the percent changes often, the presenter updates the existing spinner's message in place instead of rebuilding the indicator, so spinner cadence and frame are unaffected by progress ticks.

## Why compaction-time input goes to the engine queue

Pi's `steer` and `followUp` accept messages at any time, including during compaction, and put them in the agent's queue; only `prompt` refuses during manual compaction. The engine already emits `queue_update` for that queue, the adapter already projects it as the pending `Steering:` rows, and Alt+Up already clears it back into the editor. Routing compaction-time submissions to those two calls therefore gives visibility, editing, and restoration for free and removes the shell-private list, its `Queued during compaction` notice, and the ready-state replay whose serial awaits and command races lost messages. Extension slash commands cannot be queued and keep executing immediately through `prompt`, as pinned Pi does. Images attached to a queued message are passed to `steer`/`followUp` unchanged.

Delivery is then the engine's own behavior in every automatic case. Compaction after a run ends returns to the run loop, which continues once the queue is non-empty; compaction before a prompt is followed by that prompt, whose loop polls the steering queue at its start; overflow recovery continues the interrupted turn. Manual `/compact` is the one case with no run to return to: the session is idle when it ends, so on a manual `compaction_end` the integration takes the queue, starts one run with the first queued message through the ordinary prompt path with that message's mode, and immediately re-queues the remaining messages, which the new run's initial poll injects in order. The run is not awaited by the event handler. A failed start restores the messages to the queue and reports the failure as an ordinary command diagnostic, so nothing is dropped silently. The kick happens regardless of whether the manual compaction succeeded, was cancelled, or failed, matching pinned Pi's flush. The agent's lower-level `continue` is not used: it bypasses the session's run accounting and settlement, which the working-state lifecycle depends on.

Because Pi's queue restore returns only text, the integration keeps a small side table of the image attachments it queued during compaction, keyed by message text and consumed first-in-first-out, so a restarted queue carries its images; the side table empties on session unbind and when the queue is cleared by Alt+Up.

## What this is measured by

During a compaction whose stream is observable, the working status shows `Compacting (n%)...` with `n` rising from 0 and never reaching 100 until the label disappears at `compaction_end`; with a previous summary of length L on the branch, a stream of L/2 characters shows 50%. Without an observable stream the label is `Compacting...`. Messages submitted during manual, threshold, and pre-prompt compaction appear as `Steering:` rows immediately, are all returned by Alt+Up, and after compaction every one of them reaches the agent in submission order; a manual compaction's first queued message starts the run and the rest are injected into it. The existing tests for compaction-time image gating, large-paste queues, history recording, and invalid deferred attachments are rewritten against the new route and still hold their properties.
