- One full A1 product by default, no compatibility toggle, profile fork, separate agent, daemon, sidecar or translating service.
- One implementation per contract: shared public validation and existing launch/session/model/settings/resource/extension owners. Interactive output uses A1's custom UI; print/JSON/RPC are execution/output transports, not editions of A1.

## Audit findings

2. Neutral launch payloads support only session storage, model/provider/thinking, extensions/flags and tool exclusions. There is no public normal-product print/JSON/RPC route. `bin/ui.js` consumes internal `--runtime-options`; public input must not inherit that trust boundary.
3. `createPiRuntimeIntegration` already owns writer guards and public SDK runtime replacement. It currently creates persistent managers, resolves trust before services, adds a Windows cleanup factory, and applies limited invocation overrides. Additional session/loadout/resource/trust controls need real service plumbing, not just new flags.

Reuse these where their lifecycle and stream behavior preserve A1 invariants. They are not upstream CLI delegation. In particular their rebind/dispose hooks must compose with the existing A1 integration lifecycle rather than overwrite it.
5. Built-in CLI extensions are not automatically provided by raw SDK use. A1's current factory explicitly supplies only its cleanup extension. ## Shared architecture

```text
A1 control namespaces ----------------------> existing/extended A1 handlers
A1 explicit-prompt grammar --\
                             shared public validation -> existing launch/session services
pi naming/grammar adapter --/                           -> A1 owned interactive UI
                                                       -> public print / JSON transport
                                                       -> public RPC transport
programmatic A1 facade -------------------------------> same host/session services
```

CLI owns public syntax, help metadata and diagnostics; launch owns neutral execution intent/profile policy; foundation owns bounded structured process transport, never engine grammar. Pi integration owns public Pi types, model/credential/resource/session/transport adaptation. Composition wires product capabilities and shared integration identity; application/features retain vendor-neutral ports. Extend existing public entries and narrow contracts; do not add an unowned `compat` subsystem or relax the DAG.

Generalize the existing intent to describe transport and input sources without converting headless work into UI launch. Every ultimately selected immutable release must authenticate support for the actual request before spawn, including fallback/reselection. Shipped `a1`, the real `pi` shim, development routing and child entries must preserve original cwd and structured inputs. No fallback to upstream `main`, ambient `pi`, comparison mode or an older option-dropping release.

Machine stdout is owned before resource factories or bootstrap progress can write to it. Reuse public transport/output behavior where available; if a required output-guard facility is not public, own the small stream boundary rather than deep-import it. Route incidental logs to stderr, retain dedicated protocol writes, enforce backpressure and never add banners, ANSI reset/resume hints or color reporting to protocol stdout. RPC stdin is never consumed as piped prompt input. Metadata, large prompt/file/image input and invocation credentials need separate treatment: keep metadata bounded; carry input bodies through the existing launch chain without a universal 32-KiB public prompt truncation; do not persist API keys in settings, release seals, traces, crash diagnostics or delivery evidence. A narrowly owned process data channel may extend existing transport where platform argv limits demand it; it is not a sidecar or service.

Persistent sessions keep the same canonical-file writer admission and release-on-failure/dispose. Runtime replacement must rebind transport and product subscriptions once, cancel old callbacks, retain startup ordering and use #927's captured runtime identity/readiness/disposal. A transport is not permission to start a second endpoint or reporter. A1 APIs must operate on sessions from either entry or programmatic host whenever actual identity/storage/terminal capabilities permit them.

## Conformance strategy and evidence boundaries

The matrix distinguishes verified existing, implemented unverified, missing, conflicting and externally blocked. Existing tests were inspected, not rerun in this planning revision; no row receives verified status just because a method/flag or historical disposition exists.

- Parser tests cover every documented option/alias and meaningful constraint/precedence pair, registration, unknown/duplicate/missing inputs, reserved commands, original cwd, prompt ordering, `@file`/image and literal boundary distinctions. Paired intent tests alone cannot certify runtime behavior.
- Actual packaged public subprocesses and supported development entry routing use disposable home/profile/release/repos. Test stdin/stdout redirection defaults, strict stdout, stderr and exits; files/images/multibyte/newline/space/leading-dash inputs, and payloads above the old cap. Old/incompatible ultimately selected releases refuse rather than drop or downgrade requests.
- Print/JSON/RPC fixtures use deterministic offline providers, public SDK seams and real extensions. Compare normalized observable output to isolated pinned upstream runs where practical, with no network credentials. Mask only volatile IDs/timestamps/temporary paths, never framing, fields, event order, errors or side effects. No upstream CLI is invoked in production.
- Every RPC command and event union member gets positive/error/cancellation cases; IDs, concurrent commands, prompt dispositions, Unicode U+2028/U+2029, CRLF/LF, malformed frames, large output/backpressure, EOF, extension shutdown and platform signals are checked through pipes. JSON emits a session header, RPC does not; print length/error exits differ from JSON event failures exactly as documented.
- Test persistent/new/resume/continue/fork/clone/ID/no-session, migration of supported v1/v2/v3 history, context edits/checkpoints/branches, storage precedence, cancelled replacements, missing cwd, contention and release on failed startup/dispose. No fileless session is made durable to satisfy a test.
- Real loaded extensions exercise every lifecycle and UI family and both idle and streaming delivery. In particular idle `sendMessage(..., {triggerTurn:true})` and `sendUserMessage` must cause a turn without a keypress; `deliverAs:nextTurn` must not. One acknowledgement/turn is required, not polling until a duplicate happens to pass. Reuse existing startup/steering/follow-up/replacement fixtures.
- Parameterize #927's integration fixtures and existing UI/settings/tool-cwd tests across applicable entries/transports. Check actual capability, same captured runtime ID, live API ownership/readiness, writer fencing and cleanup; no executable-name gating or second control publisher. Terminal-only effects are tested only with a real supported host or deterministic terminal port, not claimed for every RPC child.
- Maintenance tests use temporary local package sources, scoped stores and local OAuth/MCP endpoints; no live login, GitHub upload, package installation into user state, global executable mutation or external repo modification. Help/version never load factories, and Firstmate catalog refusal is tested before marker-writing fixtures.
- Run only changed-owner test files, typecheck, strict OpenSpec and applicable architecture/startup/public-boundary checks locally. Broad tiers remain existing CI's job. Native Windows/Git Bash and supported POSIX CI evidence are recorded separately; unexecuted platforms are not certified. Do not run full/preflight/release suites for planning.
