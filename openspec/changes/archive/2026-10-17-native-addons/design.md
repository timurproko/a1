# Design

This document is written for the agent that implements the change. "Current mechanics" states how the native layer works today, verified against the files named; do not act on a different model of it. "Invariants" lists what must not change. Each decision names the files, identifiers, and the evidence that proves it landed.

## Context

### The incident

ESET Endpoint Security, managed by ESET PROTECT (the `RemoteAdministrator` agent is installed and no local quarantine directory exists), wrote `virlog.dat` at 09:13:34 on 17 October 2026 and at that moment removed `process-guardian.exe` from `releases/0.2.7-dev.788-f14eb7aa684f67b46f4c/dist/native/win32-x64/` and from the rollback release `0.2.7-dev.772-...`, plus `terminal-host.exe` from the rollback release. `a1_session_lock.node` (2 MB, built from the terminal-host crate with the `node-addon` feature) survived in both directories, and so did the untouched copy of every file under the npm global package. `npm x @timurproko/a1-install --develop` reinstalled the same version; `a1 solo` then failed in `verifyProcessGuardianArtifact` with `CONTAINMENT_ARTIFACT_MISSING`, because `runBootstrap` in `src/foundation/release/bootstrap.ts` (lines 150 to 175) takes the approved active release through `readRestartCertifiedRelease` without checking the manifest files exist. The release was repaired by hand by copying the byte-identical executable from the npm global package.

### Why the executables and not the addon

Antivirus verdicts weigh the process image. `process-guardian.exe` is 288 KB, stripped (`strip = true`, thin LTO), has no version resource (Windows Error Reporting shows `terminal-host.exe` as version 0.0.0.0 in the Application log), and is unsigned. Its Windows run path (`native/process-guardian/src/windows.rs`, `run`) is `CreateProcessW(... CREATE_SUSPENDED ...)`, `AssignProcessToJobObject`, `ResumeThread`, which is the process-hollowing prologue; `spawn_notice_watcher` then runs `std::env::current_exe()` again with `--watch-exit-notice`, a detached copy that waits for the guardian PID. `terminal-host.exe` is 5.2 MB, detaches with `CREATE_BREAKAWAY_FROM_JOB | DETACHED_PROCESS` (`launch.rs`, `configure_detached`), creates named pipes, enumerates processes with `CreateToolhelp32Snapshot` (`shell.rs`), opens other PIDs with `PROCESS_TERMINATE` (`identity.rs`), and queries tokens. Every release is a new hash, so prevalence-based reputation never accumulates. The addon runs inside `node.exe`, which is signed by the OpenJS Foundation and present on millions of machines; a DLL that never becomes a process image receives static scanning but not the behavioural attribution. The surviving file is the evidence this design rests on.

### Current mechanics the decisions depend on

Launch chain (`bin/cli.js` → detached supervisor → `bin/guardian.js` running `runLaunchGuardian` in `src/foundation/launch-guardian/main.ts` → `process-guardian` → `bin/ui.js`):

- `runLaunchGuardian` resolves `helperPath` with `resolveProcessGuardianPath(releaseRoot)` (`dist/native/<platform>-<arch>/process-guardian[.exe]`, overridable by `A1_PROCESS_GUARDIAN_PATH`), verifies it with `verifyProcessGuardianArtifact` (manifest `a1-process-guardian-artifact-v1`, SHA-256 and size), observes its own identity with the platform `NativeProcessInspector`, connects to the cohort supervisor, and creates `NativeGuardianContainment(instanceId, helperPath, <runtimeDir>/launch-instances/<id>.ready.json, <id>.exit-notice)`.
- `NativeGuardianContainment.spawn` runs the helper with `--parent-pid <node pid> --instance <id> --status-file <path> [--exit-notice <path>] -- <executable> <args...>`, `stdio: "inherit"`, env plus `A1_EXIT_NOTICE_PATH`, and polls the status file for `{ pid, startIdentity, containmentProvider, containmentToken }` (5 s). `stop(force)` sends SIGTERM or SIGKILL to the root PID; `waitForEmpty` waits for the helper to close; `close` kills the helper and removes the status and notice files. `closeVerifiedContainment` in `contracts.ts` gates cleanup on `inspector.matches(rootIdentity)` and `containment.contains(rootIdentity)`.
- Identity providers: `windows-job:<guardian pid>:<child pid>` with `windows-filetime:<ticks>`, `linux-process-group` with `linux-proc-start:<ticks>`, `darwin-process-group` with `darwin-proc-start:<sec>:<usec>`.
- `WindowsNativeProcessInspector` and `DarwinNativeProcessInspector` execute the helper with `--inspect-pid <pid>` (exit 3 means absent) and require the prefix `windows-filetime:` or `darwin-proc-start:`; `LinuxNativeProcessInspector` reads `/proc/<pid>/stat` field 22 itself. `createNativeProcessInspector` in `native-process-inspector.ts` needs a release root or the override to build the helper path.
- Exit notice (`native/process-guardian/src/exit_notice.rs`): the guardian captures console modes (Windows `GetConsoleMode` on stdin and stdout; Unix `termios`) before the runtime starts; `deliver` claims the notice by renaming it to `<path>.delivering`, reads at most 4096 bytes and 8 sanitized lines, writes `TERMINAL_RESET` (mirrors `EMERGENCY_TERMINAL_RESET` in `src/foundation/terminal-cleanup/terminal-reset.ts`) and the lines to the terminal, then restores the modes. On Windows the watcher process receives the encoded modes on its command line, `SetConsoleCtrlHandler(None, 1)`, waits for the guardian handle, waits up to 2 s for the runtime PID from the status file, and delivers.
- `test/foundation/process-containment/windows-job.integration.test.ts` and `unix-process-group.integration.test.ts` drive the executable with the flags above and run only with `RUN_PROCESS_CONTAINMENT_INTEGRATION=1` and `A1_PROCESS_GUARDIAN_PATH`; `test/fixtures/process-containment/tree.mjs` builds a root, child, and detached grandchild; `darwin-pty.py` drives foreground transfer through a pty.

Terminal host (`native/terminal-host`):

- `src/main.rs` `run_from_args` dispatches `--version`, `server`, `probe`, `release-holds`, `tabs`, `holder` (refused from the command line), `attach`, `internal`, the non-interactive probes, `--durable-replace-child`, `--controller-boundary-child`, `--resident-role-child <role> <profile> <result> <context>` (`contracts::launch::run_resident_child`), `--resolve`, and `--resolve-shell`. `main` calls `timeBeginPeriod(1)` on Windows.
- `src/launch.rs` resolves `std::env::current_exe()` as the artifact, builds a `Command` with the fixed role grammar, allowlisted environment (`PATH`, `TEMP`, `TMP`, `SYSTEMROOT`, `WINDIR` on Windows), and `configure_detached` (`setsid` plus double fork on Unix; `CREATE_BREAKAWAY_FROM_JOB | CREATE_NEW_PROCESS_GROUP | DETACHED_PROCESS` on Windows); `spawn_with_fallback` uses `spawn_via_wmi` (PowerShell `Win32_Process.Create` with `CreateFlags 0x208`) for a non-holder role from a non-resident parent.
- `Cargo.toml`: `[lib] name = "terminal_host_contracts"`, `crate-type = ["rlib", "cdylib"]`, feature `node-addon` = `napi 2.16.17` (`napi9`) and `napi-derive 2.16.13`; `src/node_addon.rs` exports `SessionLock` with `acquire`, `bindCreated`, `bound`, `release`.
- `scripts/development/build-terminal-host.mjs` builds `--bin terminal-host`, copies it, builds `--lib --features node-addon`, copies the cdylib (`terminal_host_contracts.dll`, `libterminal_host_contracts.so`, `.dylib`) as `a1_session_lock.node`, runs `--version`, writes `terminal-host-THIRD-PARTY-NOTICES.txt` and `terminal-host.manifest.json` (`a1-terminal-host-artifact-v1` with `artifact`, `sessionLock`, `notices`, `provenance.features`). `build.rs` refuses local Windows builds without `TERMINAL_HOST_LOCAL_BUILD=1` because the Zig fetch is quarantined by workstation antivirus.
- Node side: `resolveTerminalHostPath` (`ensure-terminal-host.ts`) resolves `dist/native/<platform>-<arch>/terminal-host[.exe]` or the development override `A1_TERMINAL_HOST_PATH`; `ensureTerminalHost` verifies with `verifyTerminalHostArtifact`, runs `probe`, `server --detach ...`, and polls `probe`; `maintenance.ts` and `bounded-host-command.ts` run `tabs ...` and `release-holds`; `src/foundation/session-writer-lock/index.ts` `nativeCandidates` loads `a1_session_lock.node` beside the module or from `dist/native` and `.artifacts/terminal-host` in development, with override `A1_SESSION_LOCK_PATH`.
- `attach` is the launch instance's root under the process guardian when resident tabs are enabled (`selectResidentHost` in bootstrap); `holder` is spawned by the server through the launch primitive; the server itself is spawned detached by `server --detach`.

Release surface:

- `scripts/development/build-process-guardian.mjs` builds `--release`, copies the executable to `dist/native/<platform>-<arch>/`, chmods it on Unix, runs `--version` (must contain `protocol=1`), and writes `manifest.json` (`a1-process-guardian-artifact-v1`, `artifact { filename, sha256, size }`, `provenance.identityCheck`).
- `scripts/release/verify-native-artifacts.mjs` requires, per `RELEASE_NATIVE_TARGETS`, `manifest.json` with `files: ["artifact"]` and `terminal-host.manifest.json` with `files: ["artifact", "sessionLock", "notices"]`, each recorded file present with matching size and SHA-256.
- `test/foundation/release/package-surface.test.ts` asserts the packed file list, that every packed guardian manifest's binary is recorded executable (`guardianBinaryReference` from `scripts/governance/candidate-evidence.mjs`), and that the local terminal host runs `--version`; `scripts/release/repair-native-executable-modes.mjs` and `test/repository-governance/repair-native-executable-modes.test.ts` exist only to keep executable modes.
- `scripts/release/validation-matrix.mjs` carries `binary: "process-guardian[.exe]"` and `guardian: true` on the containment lanes; `.github/workflows/ci.yml` builds the debug guardian with `cargo test` and `cargo build` and exports `A1_PROCESS_GUARDIAN_PATH`; `publish.yml` `guardians` and `terminal_hosts` jobs upload `dist/native` per runner and `package` merges them and runs `verify-native-artifacts.mjs`.
- Release materialization (`src/foundation/release/release-store.ts`): `materializeRelease` copies the package payload into `.candidate-<uuid>`, computes the release id from the content digest, and, when `releases/<id>` already exists, deletes the candidate and returns `verifyMaterializedRelease(releaseRoot)`; `verifyMaterializedRelease` checks every manifest file's digest. Files are written read-only (`0o400`/`0o500`).

## Out of scope

Signing and version resources, replacing the WMI launch path, merging holders into the server process, and any change to tab behaviour, protocol fixtures, or budgets. `proposal.md` lists the deferred items with their reasons.

## Invariants

1. No a1-built executable is produced, packed, materialized, verified, or started on win32-x64, linux-x64, darwin-arm64, or darwin-x64. Every process a1 starts has the Node runtime (`process.execPath`) as its image, with one exception kept as is: the WMI launch client `powershell.exe`.
2. The launch-instance contracts in `src/foundation/process-containment/contracts.ts` (`ProcessContainment`, `ContainedProcessHandle`, `NativeProcessInspector`, `closeVerifiedContainment` with its ownership checks and graceful-then-forced deadlines) and the supervisor protocol (`create-launch-instance`, `activate-launch-instance` with `rootIdentity` and `containmentIdentity`, stop intents) are unchanged. Identity strings keep their prefixes and provider names so retained cohort records stay readable.
3. The terminal-host protocol generation, fixtures, role grammar, credentials, endpoint ownership, registry, and the resident-tabs user-visible behaviour are unchanged; only the process image that executes a role changes.
4. The exit notice keeps its format, sanitizing, byte and line limits, claim-by-rename, and terminal reset bytes; the runtime still arms it through `A1_EXIT_NOTICE_PATH`.
5. Releases stay immutable and content-addressed: repair rewrites only files whose package source bytes match the release manifest digest and never changes a release id.
6. Budgets in `scripts/development/measure-resident-tabs.mjs` and the startup budgets are not raised to absorb Node startup; a breach is reported with its measurement.
7. Nothing is committed under `.artifacts/`; policy tests under `test/repository-governance/` are updated in the same commit as the shape they pin.
8. Decisions land as separate commits in the order 1, 2, 3, 6, 7, 4, 5, 8, 9, each leaving typecheck and the touched tests green; a decision that cannot be finished is reported, not half-applied.

## Decisions

### 1. The process-guardian crate becomes a Node-API addon

`native/process-guardian/Cargo.toml`: `[lib] name = "process_guardian"`, `crate-type = ["cdylib"]`, no `[[bin]]`; add `napi = "=2.16.17"` (`default-features = false`, `features = ["napi9"]`) and `napi-derive = "=2.16.13"` as plain dependencies; keep `windows-sys 0.61.2` with `Win32_System_Threading`, `Win32_System_JobObjects`, `Win32_System_Console`, `Win32_Foundation`, `Win32_Security`; keep `libc` on Unix. Remove `src/main.rs`'s command-line protocol, `Invocation`, `write_ready_status`, and `usage`. `strip = true` stays; a version resource is deferred.

Exported surface (`src/lib.rs`, `#[napi]`):

- `version(): { crateVersion: string; protocolVersion: 2; target: string }`.
- `inspectProcessStart(pid: number): string | null`: Windows `windows::inspect_process_start` (unchanged: `OpenProcess(SYNCHRONIZE | PROCESS_QUERY_LIMITED_INFORMATION)`, `WaitForSingleObject(0)`, `GetProcessTimes`), Darwin `darwin::inspect_process_start` (unchanged `proc_pidinfo`), Linux reads `/proc/<pid>/stat` as `LinuxNativeProcessInspector` does today so the three platforms share one entry. `null` is the established absent/dead outcome; failures throw with the current messages.
- `captureTerminalModes(): string` and `restoreTerminalModes(encoded: string)`: `exit_notice::terminal::Snapshot` with `encode`/`decode` extended to Unix (`termios` serialized as hex).
- `deliverExitNotice(path: string, encodedModes: string)`: `ExitNotice::for_watcher(path, modes).deliver()`, unchanged bytes.
- `spawnContained(options): ContainedRuntime` where `options = { executable, arguments, cwd, environment: Record<string,string>, instanceId }`. Windows: create a kill-on-close job (`configure_job` unchanged), then `CreateProcessW` with `STARTUPINFOEXW`, `InitializeProcThreadAttributeList`, `UpdateProcThreadAttribute(PROC_THREAD_ATTRIBUTE_JOB_LIST, [job])`, flags `EXTENDED_STARTUPINFO_PRESENT | CREATE_UNICODE_ENVIRONMENT`, inherited handles, no `CREATE_SUSPENDED`. The child is a job member from its first instruction. Containment token `windows-job:<node pid>:<child pid>`, provider `windows-job`. Unix: `posix_spawn` with `POSIX_SPAWN_SETPGROUP` (group 0, so the child leads its own group), `posix_spawn_file_actions_addchdir_np` for `cwd`, inherited stdio, `SIGTTOU` ignored in the caller around `tcsetpgrp` to the child group when stdin is a terminal; token `linux-pgrp:<node pid>:<pgid>` or `darwin-pgrp:...`, provider `linux-process-group` or `darwin-process-group`. The start identity is read with `inspectProcessStart` immediately after creation and the spawn fails if the child already exited.
- `ContainedRuntime` methods: `pid`, `startIdentity`, `containmentProvider`, `containmentToken`, `processGroup` (Unix), `wait(): Promise<number>` (napi `AsyncTask` blocking on `WaitForSingleObject` or `waitpid`; the exit code or `128 + signal`), `terminate(code: number)` (`TerminateJobObject` or `kill(-pgid, SIGKILL)`), `stop()` (`SIGTERM` to the group on Unix; on Windows `process.kill(pid, "SIGTERM")` from JavaScript keeps today's semantics), `close()` (Windows closes the job handle after `TerminateJobObject`; Unix runs `stop_group` with the 1.5 s TERM-then-KILL deadline and restores the saved foreground group). `Drop` closes the handles so a guardian crash still ends the tree on Windows.
- `spawnWatcher(options): number` (Windows only; Unix uses `child_process.spawn`): `CreateProcessW` of `process.execPath` with the watcher arguments, inheriting the console and stdio, with no job attribute, so the watcher is outside the guardian's job and, through the parent job's silent breakaway, outside the libuv job the guardian lives in. Returns the PID.

Details that the Rust side must get right:

- Environment and stdio: the executable inherited the environment Node gave it; the addon receives `environment` explicitly and builds the block itself (a sorted `KEY=value\0...\0\0` UTF-16 block for `CREATE_UNICODE_ENVIRONMENT`; a `char**` `envp` for `posix_spawn`). Stdio is inherited from the guardian on both platforms (no `STARTF_USESTDHANDLES`, no file actions), exactly as `stdio: "inherit"` gave the executable today.
- Reaping: libuv's `SIGCHLD` handler calls `waitpid` only for the PIDs of its own process handles, so a `waitpid(pid)` on the `AsyncTask` thread owns the child's exit status. The addon never spawns the contained runtime through libuv.
- Node-API linkage: mirror `native/terminal-host`'s configuration exactly (`napi` with `default-features = false` and `napi9`, `napi-derive`, no `napi-build`), which already produces a loadable `.node` on all three CI runners.
- Windows API additions in `windows-sys` features: `Win32_System_Threading` already covers `InitializeProcThreadAttributeList`, `UpdateProcThreadAttribute`, `PROC_THREAD_ATTRIBUTE_JOB_LIST`, `STARTUPINFOEXW`, and `EXTENDED_STARTUPINFO_PRESENT`.

`scripts/development/build-process-guardian.mjs`: `cargo build --release --locked [--target]`, copy the cdylib (`process_guardian.dll`, `libprocess_guardian.so`, `libprocess_guardian.dylib`) to `dist/native/<platform>-<arch>/process-guardian.node`, observe identity by `node -e` loading the addon and printing `version()` (through `observeExecutableIdentity` generalized to a loader command, Mach-O header check retained for the cross build), and write `manifest.json` schema `a1-process-guardian-artifact-v2` with `kind: "node-addon"`, `nodeApi: 9`, `protocolVersion: 2`, `artifact { filename: "process-guardian.node", sha256, size }`, and provenance. `native-target.mjs` gains `addonLibraryName(crate, platform)`.

Rust tests: keep `quote_windows_argument`, `build_command_line`, `inspect_process_handle`, `status_pid` tests where the function survives; add a test that `spawnContained` on the host platform places a child that itself spawns a grandchild into the same job or group and that `close()` ends both (the Rust-side equivalent of the `tree.mjs` fixture, run by `cargo test` in the containment lanes).

Evidence: `dist/native/<platform>-<arch>/process-guardian.node` with its v2 manifest in the lane's build; `cargo test` green on all three runners.

### 2. The launch guardian contains the runtime in-process

`src/foundation/process-containment/`:

- New `addon.ts`: `loadProcessGuardianAddon(path)` through `createRequire` with a typed interface mirroring Decision 1; one cached instance per path; a load failure throws `CONTAINMENT_ARTIFACT_MISSING` or `CONTAINMENT_ARTIFACT_INCOMPATIBLE` with the message.
- `artifact.ts`: `verifyProcessGuardianArtifact` accepts schema `a1-process-guardian-artifact-v2`, `kind: "node-addon"`, `protocolVersion: 2`, same digest and size checks; the v1 schema is rejected as incompatible.
- `native-guardian-containment.ts` becomes `addon-containment.ts` exporting `AddonContainment implements ProcessContainment`: `spawn` calls `spawnContained`, stores the `ContainedRuntime`, sets `identity` from the token and provider, and returns `{ identity: { pid, startIdentity }, outcome }` where `outcome` is `wait()` mapped to `{ kind: "exited", exitCode }`, `{ kind: "signaled", signal }` for `128 + n` on Unix, or `{ kind: "guardian-error" }` on a rejected wait. `contains`, `stop`, `waitForEmpty` (resolves when `wait()` settles or the timeout passes), and `close` keep their semantics; the status file is no longer written, because the identity is returned directly. `resolveProcessGuardianPath` resolves `process-guardian.node`; `A1_PROCESS_GUARDIAN_PATH` keeps naming the file to load.
- `windows-process-inspector.ts` and `darwin-process-inspector.ts` collapse into `addon-process-inspector.ts`: `AddonProcessInspector(addonPath, identityPrefix)` calls `inspectProcessStart`; `null` is absent; the prefix check and PID check are unchanged. `LinuxNativeProcessInspector` stays as the procfs reader (it needs no addon) and `createNativeProcessInspector` picks it on Linux as today.
- `src/foundation/launch-guardian/main.ts`: before spawning, capture `encodedModes = addon.captureTerminalModes()` when `exitNoticePath` is set; spawn; immediately after `spawn` returns and before `activate-launch-instance`, start the watcher (Decision 3) with the runtime PID and, on Unix, the process group; after the outcome, deliver the notice from the guardian itself with `deliverExitNotice(path, encodedModes)` exactly where the executable did (`notice.deliver()` after `run_contained`), so the ordinary paths need no watcher. A guardian killed in the few milliseconds between spawn and watcher start loses only the notice; the job or the group cleanup does not depend on the watcher on Windows. The `GuardianControl`, stop requests, `requireAccepted`, and exit-code mapping are unchanged.
- `product-identity.json` artifacts: `processGuardianExecutable` becomes `processGuardianAddon: "process-guardian"`; `product-identity.ts` `ARTIFACT_KEYS` follows; the governance checks that enumerate artifact keys are updated.

Tests: `test/foundation/process-containment/artifact.test.ts` (v2 manifest accepted, v1 incompatible, missing and tampered unchanged), `addon-process-inspector.test.ts` (replaces the Windows and Darwin inspector tests with a fake addon), `test/foundation/launch-guardian/launch-guardian.test.ts` (fakes already inject `containment` and `inspector`; `ensureHelper` remains the artifact seam; add the capture-deliver order), `contracts.test.ts` unchanged.

Evidence: `a1 solo` on this workstation launches with no `process-guardian.exe` in the release; `tabs doctor` and `a1 version` unchanged.

### 3. A Node-hosted exit watcher outside the guardian's containment

New entry `src/foundation/launch-guardian/exit-watcher.ts` (compiled to `dist/foundation/launch-guardian/exit-watcher.js`, listed in the runtime payload inventory): arguments `--guardian-pid <n> --notice <path> --modes <encoded> --addon <path> --runtime-pid <n> [--process-group <pgid>] [--foreground-group <pgid>]`. The executable's status file is gone, so the guardian passes the runtime PID and group on the command line; the watcher is therefore started right after the spawn (Decision 2), not before it. It loads the addon, ignores `SIGINT`/`SIGTTOU` (Windows: the addon's `SetConsoleCtrlHandler(None, 1)` wrapped as `ignoreConsoleControl()`), waits for the guardian with `waitForProcessExit(pid)` (addon: Windows `WaitForSingleObject` on a `SYNCHRONIZE` handle in an `AsyncTask`; Unix a 25 ms `kill(pid, 0)` poll, `EPERM` counting as alive), then on Unix runs the bounded TERM-then-KILL group cleanup through `stopProcessGroup(pgid)` and restores the saved foreground group, on Windows waits up to 2 s for the runtime PID, and finally calls `deliverExitNotice`. Whichever of guardian and watcher renames the notice first delivers; the other finds nothing, exactly as today.

Starting it: on Windows `spawnWatcher` from Decision 1 (console inherited, outside both jobs); on Linux and macOS `child_process.spawn(process.execPath, [entry, ...], { stdio: "inherit", detached: false })`, which keeps the watcher in the guardian's session and process group so it may `tcsetpgrp` after ignoring `SIGTTOU`; terminal hang-up then reaches it with everything else, which is the case where nothing needs restoring.

Accepted gap, recorded in `docs/architecture/process-guardian-provenance.md` and the lifecycle spec: a kill that targets every Node process (`taskkill /IM node.exe`, `pkill node`) ends the watcher with the guardian and runtime, so no notice is printed and, on Unix, non-Node descendants of the runtime group are not signalled. The previous executable survived that case. Terminal closure, `Ctrl+Break`, a crash of the guardian, a kill of the runtime PID, and a kill of the guardian PID are all still covered.

Tests: `windows-job.integration.test.ts` and `unix-process-group.integration.test.ts` are rewritten around a Node owner fixture (`test/fixtures/process-containment/owner.mjs`) that loads the addon from `A1_PROCESS_GUARDIAN_PATH`, contains `tree.mjs`, and starts the watcher: the four existing Windows scenarios (stable identity and death, root plus detached child and grandchild end when the owner is killed with the unrelated sibling surviving, notice after a force-killed runtime and silence after a clean exit, notice from the watcher when the owner is force-killed) and the Unix group and Darwin pty scenarios keep their assertions with the owner fixture in the guardian's role. `darwin-pty.py` runs the owner fixture instead of the executable.

### 4. Terminal-host roles exported from the addon

`native/terminal-host`:

- Move `run_from_args` and every role command from `src/main.rs` into the library (`src/roles/entry.rs`), keeping the dispatch table and messages; `src/main.rs` is deleted and `[[bin]] fake-tab` stays (it is a test fixture built only with `resident-fixtures`, never shipped).
- `src/node_addon.rs` exports, beside `SessionLock`, `runRole(arguments: string[], host: { executable: string, entry: string }): number`. It sets the process-wide host command once (`launch::set_host_command`), calls `timeBeginPeriod(1)` on Windows, runs the dispatch on the calling thread, and returns the exit code; the JavaScript entry exits with it. `std::process::exit` calls inside roles are replaced by returned codes so Node's exit path runs. `version(): object` returns the `--version` provenance JSON.
- `src/launch.rs`: `current_exe()` is replaced by the recorded host command: the spawned `Command` is `<executable> <entry> --resident-role-child <role> <profile> <result> <context>`, and `spawn_via_wmi` builds the same command line. The grammar, environment allowlist (extended with the variables Node needs to start: none beyond `SYSTEMROOT` and `PATH` on Windows; `HOME` is not needed), `configure_detached`, identity verification, and `run_resident_child` are unchanged. The verified artifact for admission is the addon file the entry loads, recorded in the result exactly as the executable path was.
- `Cargo.toml` keeps `crate-type = ["rlib", "cdylib"]`; the `node-addon` feature now gates only the napi glue; `fault-injection` and `resident-fixtures` stay off in release addon builds and `verifyVersionReport` keeps asserting that.

Node entry `src/foundation/resident-tabs/host-entry.ts` (compiled to `dist/foundation/resident-tabs/host-entry.js`): resolves the addon beside itself (`../../native/<platform>-<arch>/terminal-host.node`) or `A1_TERMINAL_HOST_PATH` under the development instance id, loads it with `createRequire`, installs no-op `SIGINT`, `SIGTERM`, and `SIGHUP` listeners so Node's default signal exit cannot pre-empt the role's own handling (the attach role owns raw mode and `Ctrl+C` semantics; the server and holder own their shutdown protocol), calls `runRole(process.argv.slice(2), { executable: process.execPath, entry: __filename })`, and exits with the returned code. It touches no `process.stdin`/`stdout` stream objects so the console handles stay with the Rust role. `bin/` gains no new file; `package.json` `files` already ships `dist`.

Per-tab cost: a holder is now a Node process (about 30 to 40 MB resident on Windows against a few MB before). `measure-resident-tabs.mjs` keeps its budgets (`warmCreateMs` 250 ms, `reattachPaintMs` 300 ms, direct startup 2500 ms); the first Windows terminal-host lane records the new values in `docs/architecture/resident-tabs.md`. If a budget is breached the number is reported and the decision is revisited, not the budget.

Tests: a libtest binary cannot accept the role grammar, so a fixture `[[bin]] name = "role-host"` (`tests/fixtures/role-host/main.rs`, `required-features = ["resident-fixtures"]`, beside `fake-tab`) calls `run_from_args` on its arguments; `native/terminal-host/tests/role_integration.rs` and the fixture roles call `launch::set_host_command(role_host_path, [])` so the primitive spawns `role-host --resident-role-child ...`, and the suite needs no Node. The release addon never carries that binary. `scripts/development/run-terminal-host-probe.mjs` loads the debug addon from Node and runs `version()` and the non-interactive probes through `runRole`, and copies it to `.artifacts/terminal-host/terminal-host.node` for the development launcher.

### 5. Node resident-tab code uses the addon and entry

### 8. Bootstrap repairs a damaged certified release

`src/foundation/release/bootstrap.ts`: before `readRestartCertifiedRelease(active, ...)`, call `assertCertifiedFilesPresent(active.releaseRoot)` (new in `release-store.ts`: `stat` of every manifest file, no digest pass). When a file is missing, or when `readMaterializedRelease` later reports a digest mismatch, call `repairMaterializedRelease(options.packageRoot, active.releaseRoot)`: discover the package payload as `materializeRelease` does, and for each manifest file that is missing or differs, require the package source bytes to hash to the manifest digest, write them with the recorded mode (`wx` into a temporary name in the same directory; for an altered file first `chmod` the read-only target to `0o600`, then rename over it, then `chmod` to the recorded mode, because Windows refuses to replace a read-only file), and finally `verifyMaterializedRelease`. A file whose source does not match the manifest, or a package version that differs from the release, makes repair fail with `RELEASE_REPAIR_UNAVAILABLE`, and bootstrap continues on the existing path (which materializes the installed package as a new release when its version differs). Repair never deletes or renames a release directory and never touches dependency layers (their own verification is unchanged). The same check runs in `materializeRelease` when `releases/<id>` already exists, so a reinstall of the same version repairs instead of failing verification.

Tests: `test/foundation/release/release-store.test.ts` (missing file repaired from a matching package, mismatched source refused, modes restored), `bootstrap.test.ts` (fast path refused for a damaged release, repair then launch).

Evidence: delete `process-guardian.node` from the active release on this workstation, run `a1 version`, observe the file restored and the launch succeed.

## Risks

- A static scanner may still flag a `.node` file; this change removes the behavioural and reputation signals, not every signal. Decision 8 makes such a deletion a repaired condition rather than a dead install, and signing is the deferred next step.
- Node startup adds to holder creation and attach time; budgets are kept and measured, not raised.
- `posix_spawn` with `POSIX_SPAWN_SETPGROUP` and `addchdir_np` needs glibc 2.29 and macOS 10.15, both older than the supported platforms.
- The job-list thread attribute needs Windows 10 1607; a1 supports Windows 10 and 11 only.
- Blocking the Node main thread inside `runRole` is intended: the role owns the process. Any future JavaScript in the entry must run before `runRole`.
