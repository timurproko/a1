## Context

Two scheduled workflows validate `develop` every night: `full-regression.yml` runs every owner on four lanes and uploads `full-regression-<sha>-<run>-<attempt>-<os>-node<n>` artifacts holding `full-regression.json` (per-owner `id`, `exitCode`, `durationMs`, `scopes`), the phase `.jsonl` records, and receipts; `release.yml` runs the same complete validation before publication. Neither records failing test names in structured evidence: the vitest default reporter writes them to the job log only, and `createValidationPhaseRecorder` deliberately records no command output. `pi-upstream-sync.yml` with `propose-pi-upgrade.mjs` and the pure `pi-upgrade-report.mjs` is the existing shape for a nightly job that pushes a branch and opens or refreshes a draft pull request with the archive App identity.

## Decisions

- **Trigger:** `workflow_run` on `workflows: [Full regression, Release]`, `types: [completed]`, gated in the job by `conclusion == 'failure'` and, for `Release`, `event == 'schedule'` so manual publication requests never open triage. Manual `Full regression` dispatches do trigger triage, because the runbook uses them for pre-merge risk checks and a failure there is the same evidence. A `workflow_dispatch` input takes a run id for reruns and dry runs.
- **Evidence sources, in order of trust:** the uploaded tier result per lane (`full-regression.json`, or `<platform>.json` on a release lane; schema `a1-validation-outcomes-v1`) is authoritative for which commands failed, with their `scopes` as the owner names and the test files read from the command's own positive arguments (`--exclude` operands are not what it ran); `gh run view <id> --log-failed` supplies the excerpt, filtered to vitest `FAIL`, `×`, `AssertionError`, `Error:`, and `expected`/`received` lines, bounded to 40 lines per owner and 2 KiB, so a body never carries a whole log. When a lane failed before producing `full-regression.json` (install, pack, or Defender step), the failed job name and its last bounded log lines are the evidence and the owner list is `orchestration`.
- **Suspect commits:** the last successful run of the same workflow on `develop` (`gh run list --workflow <file> --branch develop --status success --limit 1 --json headSha`) bounds `git log --first-parent <lastGreen>..<head>`; each commit is listed with its pull-request number. No success in the retained window lists the head only and says so.
- **Dedupe key:** the workflow file plus the sorted failed scope ids (plus `orchestration` when a lane died early), written as a visible `- Triage key: \`...\`` bullet under `## Implementation`; the `openspec-implementation` fence rejects unknown keys, so the key does not live there. An open pull request whose branch starts with `fix/nightly-regression-` and whose key equals the new one is refreshed: the new run's evidence is appended under `## Implementation` and under `## Evidence` in the change's `design.md`; the branch is not force-pushed. A different key opens a new pull request; the older one stays open for the maintainer.
- **Branch and scaffold:** `fix/nightly-regression-<yyyy-mm-dd>` (suffixed with the run number when that day's branch already exists for a different failure) from the failed head, one commit `chore(regression): propose the fix for the <date> nightly failure` adding only `openspec/changes/fix-nightly-regression-<date>/` (`.openspec.yaml` with `skip_specs: true`, `proposal.md`, `design.md`, `tasks.md`). The proposal restates the evidence in prose; tasks are unchecked reproduce/fix/prove items so the maintainer's implementation continues in the same pull request without reshaping it. No spec delta is scaffolded; `openspec status` reports the `specs` artifact as `skipped`, which is the state finalization's `delta-missing` check accepts, and the proposal tells the fixer to drop the skip when a delta is added.
- **Authority:** reads (`run view`, `run download`, `run list`, `pr list`) use the workflow token through `GH_READ_TOKEN`; the push and the pull-request create/edit use the App token so downstream workflows run; `develop` is read only; the pull request is created with `--draft` and never marked ready. The workflow is listed in `config/github-repository-governance.json` with a new `nightly-regression-triage` authority recognised by `inspectWorkflowSource` when the source runs `propose-regression-fix.mjs`.
- **Proof rule:** ordinary PR validation selects owners by impact and never runs exhaustive owners, so a fix candidate could go green without exercising what the nightly failed on. The delivery rules (`openspec/config.yaml`, the change-delivery skill, the runbook) therefore require a dispatched Full regression of the completed fix head, recorded in the design evidence, before hand-off; the scaffolded task 3.1 names the command. This is a rule the agent follows, not an automated gate: a push-triggered Full regression on every candidate push would cost four 40-minute lanes per push.
- **Failure of the triage itself** (artifact missing, `gh` error, push rejected) fails the triage workflow with the reason in its summary and never retries the nightly; the email the maintainer already receives remains.

## Risks / Trade-offs

- Log-excerpt filtering is heuristic; a failure with an unusual reporter line shape yields a thin excerpt. The owner and test-file lists remain authoritative and the run link is always present, so the excerpt is a convenience rather than the evidence of record.
- A persistent failure that recurs nightly is refreshed on the same pull request rather than piling up candidates; a flaky owner that fails on alternating nights therefore produces one candidate whose evidence list shows the pattern.
- The workflow file only runs from `develop`, so its first real execution is after merge; the script was dry-run locally against the real failed run #24 (`dependency-policy` on three lanes plus a build-receipt orchestration failure on Windows Node 22) and produced the expected body, and the `workflow_dispatch` `dry_run` input is the post-merge check.
