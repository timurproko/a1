# Tasks

Milestone 3 of 6 for resident tabs (see `docs/architecture/resident-tabs.md`). Implementation starts only after the user approves this plan and milestone 2 has merged.

Unless a task says otherwise, native tests live under `native/terminal-host/tests/` and run in the three-platform terminal-host CI matrix from milestone 1 (Windows x64, macOS, Linux). A result on one platform is never recorded for another.

## 1. Baseline

- [ ] 1.1 Rebase on `develop` with milestones 1 and 2 merged. Record in `design.md` the actual module paths that milestone 2 used for the server, holder, attach shells, and the registry. Record the in-process session-lock binding that milestone 1 pinned. If milestone 1 provides only an out-of-process lock, add the in-process binding (task 6.1) before any wiring task.

## 2. Sans-IO cores and the execution shell

- [ ] 2.1 Move the server and holder state machines into `native/terminal-host/src/core/` (`core/server.rs` and `core/holder.rs`, new files) as pure `step(state, event, now) -> effects` functions with the typed effects from design Decision 3. Prove it with unit tests. Add a governance test that fails if `core/` imports `std::fs`, `std::net`, `std::process`, `std::thread`, or platform modules.
- [ ] 2.2 Add a bounded worker pool with per-effect deadlines (new file `native/terminal-host/src/shell/workers.rs`) that turns completion into `Completed` and expiry into `DeadlineMissed`. Late results are discarded by incarnation, and the role fails fast when 8 workers are abandoned. Prove it with unit tests using a fake clock and with platform tests where a blocked identity check or fsync misses its deadline while the loop keeps serving pings.
- [ ] 2.3 Add an independent watchdog thread per role (server, holder, attach): 1 s ticks, a 15 s stall limit, and an owner-only JSON crash record, then abort of that process only. Route core invariant violations through the same path. Prove it on each platform by freezing one role's loop with fault injection and asserting that only that process ends and the record exists.
- [ ] 2.4 Add the `fault-injection` cargo feature and the hook points listed in design Decision 9. Release builds must refuse the hook variables at startup. Prove it with a test that a release-profile build ignores them and reports refusal.
- [ ] 2.5 Add a deterministic simulator (new `native/terminal-host/src/core/sim/`) that drives both cores with a seeded scheduler over holder, child, and server death, message loss, reordering, delay, stale epochs and incarnations, duplicate start requests, slow clients, and start-budget exhaustion. It checks these invariants: one registry writer, one live holder incarnation per tab, one session writer per session, no committed mutation lost, no command accepted from a lower epoch, and convergence to running, stopped, `holder-lost`, or `failed`. A failure prints the minimized event sequence. Run 10,000 seeds in CI and 1,000,000 seeds as a manual target recorded in evidence.

## 3. Two or more tabs and client lanes

- [ ] 3.1 Extend the server topology and registry to N tabs (bounded by `tabsMax` from milestone 2, or 10 if absent), each with its own holder, endpoint `…-h-<tabId>`, and incarnation counter. Add the hidden `a1-terminal-host internal tab-create|tab-list|tab-close` route and `attach --view <tabId>` from design Decision 1. They are gated on `residentTabs`, authenticated by the client token, and absent from help. Prove two-tab create, list, view, and close on each platform, and prove that the route is refused when `residentTabs` is off.
- [ ] 3.2 Add the per-client control lane (1024 frames or 4 MiB, overflow closes with `client-overrun`) and single-slot render lane with stale marking and full-surface resync on drain. The server subscribes to holder patches only while some client views the tab. Prove it with core unit tests and with a platform test where one client stops reading for 30 s while two tabs stream: the other client's input-to-echo latency stays within 2x baseline, holders never block, registry commits continue, and the stalled client receives a full surface on resume.
- [ ] 3.3 Make the holder's outgoing patch stream to the server a single slot, so a stalled server never blocks the PTY reader. Prove it with a platform test that freezes the server loop through fault injection while `fake-tab` writes 50 MiB, and asserts the child never blocks and the holder model holds the final screen.
- [ ] 3.4 Show a read-only surface to a second client viewing an already controlled tab, with input and resize from it refused with a typed reason. Prove it with a platform test using two attach clients.

## 4. Holder supervision and PTY flow control

- [ ] 4.1 Send holder heartbeats every 5 s. The server counts a miss only while its own loop and the holder connection are healthy, and after 3 misses it verifies identity and terminates gracefully then forcibly within deadlines, then marks the tab `holder-lost`. Prove it with a simulation case for "server stalled, holder healthy → no accusation" and a platform test that hangs one of two holders and asserts that only it is terminated within 20 s while the other tab keeps echoing input.
- [ ] 4.2 Add a dedicated PTY reader and writer thread per holder, a 1 MiB bounded input queue, whole-paste capacity reservation, in-order queueing while starting, `input-rejected{not-accepting-input}`, and `input-uncertain{admittedBytes, writtenBytes}`. The attach client shows rejection and uncertainty as a one-line notice on row 0. Prove it per platform with `fake-tab` cases: a stalled reader plus a paste is rejected with no prefix delivered; keystrokes typed during start arrive in order; a child killed mid-paste yields `input-uncertain` and no replay; a blocked ConPTY or PTY write does not stall the holder loop or heartbeats.
- [ ] 4.3 Add PTY-creation-hang and spawn-deadline handling. A holder whose PTY creation exceeds 5 s is terminated by the server and retried, at most 3 attempts per start, and then the tab is `failed` with the reason. Prove it on each platform with the hang hook in one new tab while another tab streams, asserting the server answers pings throughout.

## 5. Server replacement and fencing

- [ ] 5.1 Add the start gate (`server-start.lock`), `starts.json` with the budget of 3 starts in 60 s, and the ordered start sequence from design Decision 4: probe, verify and terminate the owner, lease, budget, epoch, marker, bind. Clients and holders request replacement through milestone 1's verified `server --detach` recovery path with jittered backoff. Prove it with per-platform tests: a client and a holder racing to replace start exactly one server; an unverifiable owner yields `host-recovery-blocked` and no second writer; the fourth crash in 60 s yields the stopped state, and `[r]` starts again.
- [ ] 5.2 Add holder re-admission with derived credentials, pid and native start identity, holder and child identity, incarnation, and highest-seen epoch. Holders and bridges reject lower epochs. Tabs whose holders are gone or unverifiable become `holder-lost`, and no new writer starts. Prove it with the per-platform fixture "two tabs, kill server": both holders are re-admitted with unchanged holder and child pids and start identities, the client shows current surfaces, and a delayed command from the old epoch is rejected by holder and bridge.
- [ ] 5.3 Add crash-point tests that kill the starting server at each named point (after lease, after epoch, after marker, after bind, before and after each registry commit) and kill the running server during a registry commit. The next start must load the complete old or new registry, never start empty, and re-admit the same holders. Run every point on each platform.
- [ ] 5.4 Add stale pid and epoch fixtures: a recorded holder pid reused by an unrelated process is neither adopted nor terminated, and a stale `holder.exit` from a superseded incarnation is discarded while the new incarnation keeps running. Prove each per platform and in simulation.

## 6. Session-writer guard on every route

- [ ] 6.1 Add `src/foundation/session-writer-lock/` (new) wrapping milestone 1's in-process lock binding: `acquireExisting`, `reserveNew`, `bind`, `release`, and `SessionWriterConflict` naming the holder kind. Prove it with `test/foundation/session-writer-lock/*.integration.test.ts` on each platform: aliases (case, symlink, junction, hard link), reservation-to-bind with no gap, release only on writer exit, and no host, holder, or bridge started.
- [ ] 6.2 Wire startup in `src/integrations/pi/engine/runtime-integration.ts` (`createPiRuntimeIntegration`, `SessionManager.create`, `openSelectedPiSession` and its `forkFrom`) and `session-selection.ts`. Direct conflicts offer the existing explicit fork prompt (`src/features/owned-ui/session-fork-prompt.ts`), and declining exits nonzero with `session is open in another A1 process`. Prove it with integration tests for bare `a1`, `a1 --session` (by id, by path, and by alias), and `a1 pi`, each with `residentTabs` both on and off.
- [ ] 6.3 Wire every in-runtime replacement: the runtime factory and `replacePiRuntimeSession` in `runtime-integration.ts`, `new-session` and `resume-session` in `adapter.ts`, and `newSession`, `switchSession`, `fork`, and `importFromJsonl` in `workflow-runner.ts`. Acquire the target before release, and keep the old session and its lock on failure. Prove it with tests that a switch to a held session is rejected with the old session still active and locked, and that new and fork targets are bound before Pi's first append.
- [ ] 6.4 Guard the picker's `renameSession` in `src/integrations/pi/engine/workflow-contexts.ts` with a short-lived lock, and refuse with a notice when the session is held. Prove it with a test that renaming a session open in another process is refused and the file is unchanged.
- [ ] 6.5 Use the same guard in the resident tab child (`node bin/ui.js --tab`). A held session reports `session-held` and the tab does not start. Prove it with a platform test: kill a holder while its child still runs, and assert that the replacement cannot open the session until the child's exit is verified.
- [ ] 6.6 Add `scripts/governance/check-session-writer-guard.mjs` (new), wired into `check:architecture`. It rejects `SessionManager.create`, `.open`, `.forkFrom`, and `.continueRecent` in production `src/` and `bin/` code outside the guarded owners. Prove it with a fixture violation test.

## 7. Concurrent starts and graceful stops

- [ ] 7.1 Declare `tabsMaxConcurrentStarts` (default 2, hard cap 8) in `src/ui/settings/declarations.ts` and pass it to the server. The server enforces at most that many child starts in flight, at least 250 ms apart. Prove it with core unit tests and a per-platform test that starts ten real A1 tabs at once and asserts every tab reports its configured models available, with `auth.json` and settings intact.
- [ ] 7.2 Stop tabs gracefully first (server shutdown request over the bridge, or PTY input close without a bridge) and forcibly after the deadline, verifying tree exit before releasing the tab. Prove it per platform: six busy tabs stopped at once all reach stopped or a reported termination failure within the bounded deadline while the server answers pings; a cooperating tab exits without force and leaves no stale profile lock; a `fake-tab` that ignores shutdown is terminated by force.

## 8. Isolation fixtures

- [ ] 8.1 Add the `fake-tab` fixture binary (new `native/terminal-host/tests/fixtures/fake-tab`) with streaming, stop-reading, hang, exit, ignore-shutdown, and grandchild modes, built for all three platforms.
- [ ] 8.2 Add per-platform isolation suites: an isolated child death and an isolated holder death each leave the other tab and the server unaffected; a child hang (not reading input) leaves the other tab's input-to-echo latency within 2x baseline; an attach-client kill leaves all resident processes running with unchanged identities; ten server kills in one minute with five streaming tabs leave every tab process identity unchanged, and an explicit restart reattaches all five tabs with complete retained screens.
