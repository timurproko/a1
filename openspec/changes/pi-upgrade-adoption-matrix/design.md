# Design

## What the reviewer still did

The 0.85.1 proposal is the measurement. The bot's commit changed 38 files (5,949 insertions); the reviewer's eleven commits changed 94 files (1,250 insertions, 4,710 deletions). The deletions are almost entirely four copies whose three-way merge produced conflict blobs (text helpers 1,777 lines, theme unit 1,628, theme controller 334, owned editor 240) that the reviewer replaced with A1's version, because the ledger already records those copies as reduced adaptations that do not follow upstream. The insertions fall into five kinds of work, and each kind maps to one item below: resolving 17 conflict hunks in the copies that do follow upstream (already the driver's job, and now the only merge output); adopting changed public shapes (`SettingsConfig`, the model selector constructor, `OverlayHandle.getBounds`, the split scrollbar styles, `ThemeBg` versus foreground colors); deciding what A1 does with new upstream features (the `/thinking` command, `modelThinkingLevels`, `fullscreenCopyOnSelect`, the default-model action); re-anchoring seven orphaned inventory entries and classifying five new upstream units; and mechanical pin work (startup-graph numbers, version literals in tests, a generator that ran without the resolver hook). The first three kinds are decisions and stay with the reviewer; the last two are input the driver can produce.

## The API surface is a baseline, not a compile error

Both packages export through a package-root entry with a short declaration file that re-exports from `dist`. The refresher loads each entry through the TypeScript compiler API, walks the exported symbols, and records for each one its kind (class, function, interface, type, const), the hash of its normalized declaration text (members and signatures, comments stripped), and the A1 modules under `src/` whose import statements name it (94 symbols today: 37 from the coding agent, 57 from the TUI). Declaration files are read by path from the installed package, like the settings metadata refresher already does; the baseline is tooling evidence, never a production import, so the boundary rule that forbids deep imports is untouched. The driver's `public-api` step runs the refresher against the candidate into the artifact directory and diffs it against the committed baseline: an export that disappeared or changed hash and has consumers is an adoption item naming the consumers; one that appeared is a candidate the matrix may want; one that changed without consumers is listed but not flagged. The evaluator's compile output is kept whole in the artifact and summarized in the body as one line per file with the error count, so the reviewer reads "session-shell.ts: 3 errors, ThemeBg" instead of a 400-character prefix.

## Matrix rows come from upstream, dispositions from A1

The interactive baseline's manifests already enumerate what pinned Pi presents: 22 advertised commands, 3 hidden routes, 47 TUI and 42 app keybindings, 21 session events, 33 settings callbacks, 24 stateful components; the settings metadata lists the 31 presented settings; the changelog resource carries the "New Features" headings per version. The matrix turns those into rows with stable ids (`command:thinking`, `setting:modelThinkingLevels`, `keybinding:app.interrupt`, `event:agent_start`, `component:CustomEditor`, `changelog:0.85.1:fullscreen-copy-on-select`) and adds the one thing upstream cannot know: what A1 does about each. `pinned` means the pinned component is reused as is; `owned` names the behavior id in the interactive baseline and the test that proves it; `diverged` names the approved deviation in the ledger; `declined` carries a reason; `pending` is the state of every row the refresher creates. The refresher rewrites the upstream side of every row and never touches a disposition, so the matrix survives regeneration like the ledger's reviewed fields do. A governance suite reads the matrix on every pull request: no row may be `pending` on `develop`, an `owned` row's behavior and test must exist, a `diverged` row's deviation must exist, and a row whose upstream feature is gone is `retired` until a reviewer removes it. The driver's `matrix` step is the same refresher run against the candidate: rows it creates are the "new upstream features" section of the body, rows it retires are review items. The reader's `a1 pi` versus owned-UI comparison then has a checklist that names the surfaces the upgrade added rather than the whole product.

## Copies A1 keeps are not merged

Each `owned-presentation` record gains `upgradeStrategy`. `three-way` is the current behavior. `keep-owned` marks a copy whose modifications are a reduction or a rewrite of upstream rather than a port with deviations; the driver skips the merge, writes the upstream delta (`git diff --no-index` of old and new upstream) to the artifact, and lists the copy as "upstream changed, A1 version kept" with the delta's line count so the reviewer can decide whether anything in it is worth carrying over. The four copies named above start as `keep-owned`; the field is reviewed like classification, so the updater preserves it.

## Blocked is not failed

A conflict marker is a syntax error, so every gate that compiles the tree fails after a conflicted merge and the body reports six failures caused by one. The driver now checks the merged copies for markers after the `merge` and `ledger` steps and records `parity`, `typecheck`, `architecture`, and `parity-suites` as `blocked` with the conflicted paths when any remain; they run when the merge is clean or after a `refresh` on a branch where the reviewer resolved them. The evaluator's isolated compile and the engine conformance run do not depend on the copies and stay as the candidate's verdicts. The startup-graph baseline is re-pinned by a step that runs the existing report and writes the new totals, since the numbers change on every upgrade and carry no decision.

## A proposal branch belongs to whoever committed last

Before pushing, the workflow reads the remote proposal branch: if it does not exist, or every commit above `develop` is the bot's own proposal commit, the branch is recreated and force-pushed as today. If any commit above `develop` has another author, the branch is left alone, the fresh report is posted as a pull-request comment headed with the version and date, and the run succeeds; the reviewer's work is never replaced by automation. The body refresh writes only the report between `<!-- pi-upgrade-report -->` and `<!-- /pi-upgrade-report -->`, so the proposal and implementation sections a reviewer edits survive, and the OpenSpec scaffold is written only when the change directory does not exist. Manual dispatch gains a `refresh` input: with it, the driver checks out the existing proposal branch, skips `bump`, `evaluator`, `install`, and `merge`, and re-runs the derived steps and gates on the reviewer's head, which is how a reviewer asks for a fresh verdict list halfway through.
