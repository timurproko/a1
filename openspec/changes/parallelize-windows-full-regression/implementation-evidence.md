## Implementation evidence

- `scripts/release/validation-tier.mjs` keeps building the complete deduplicated `full-release` plan first. `partitionFullRegressionPlan` assigns every canonical command and Vitest invocation to exactly one of the stable `core`, `resource`, `rendering`, and `package` shards through an explicit reviewed table; an unassigned, doubly matched, or duplicated id, a shard with no invocation, or a non-`full-release` plan throws. `candidate-build` is the only per-shard prerequisite, and `exact-package-preparation` belongs to the package shard. `fullRegressionPlanDigest` hashes the platform-independent plan (the absolute candidate path is excluded), so Windows shards and the Linux collector agree on one identity.
- The exhaustive published-predecessor test is now an explicit `vitest-update-predecessor` invocation (`vitest run test/foundation/release/update-predecessor.integration.test.ts --testTimeout=30000`, the same bound it had in the ordinary invocation) and is excluded from `vitest-full-without-isolated`. Its predecessor count, phase limits, oracle, and assertions live in the unchanged test. The unsharded Linux, macOS, local, and publication plans still run it exactly once.
- `createFullRegressionShardPlan` restricts the canonical plan to one shard without changing any invocation arguments or evidence. Non-package shards carry no pack command and no exact-package preparation; the package shard keeps startup before contracts. `run-validation-tier.mjs --full-shard <id>` runs that plan and writes the shard identity (`a1-full-regression-shard-v1`: id, plan digest, prerequisites, assigned work) into the result; `--prepare-exact-package` still prepares for the canonical consumers so the package shard's handoff matches.
- `scripts/release/full-regression-evidence.mjs --record-shard` binds each shard result, passed or failed, to source, base, PR, selection, run, attempt, runtime, and shard. `mergeFullShards` requires all four expected shards once each from the same context and runtime, the same canonical digest, prerequisites, and assignment, a passed result with no failed outcome, and outcomes that exactly equal the assigned work. It then rebuilds an ordinary `a1-validation-outcomes-v1` result in canonical order with shard-attributed outcomes and shard timing (`elapsedMs` across overlap and summed `runnerMs`). `--merge-shards` writes it, and the unchanged `--record` binds it to `windows-2025-node22` or `windows-2025-node24`. The required aggregate still accepts exactly four lanes.
- `.github/workflows/full-regression-shared.yml` replaces the two Windows matrix entries with a `windows-shard` matrix (Node 24 and 22 × four shards, fail-fast off, 40 minutes, no retry or `continue-on-error`). Each shard checks out, installs, builds, and records its own build receipt. Only the package shard packs, prepares the exact installation, and enables Defender before first-attempt startup; startup evidence and its summary come only from that shard. Every shard always uploads its result, shard record, receipts, and phase evidence under a name carrying source, run, attempt, runtime, and shard. A `windows-lane` job per runtime (`if: always()`) downloads only its runtime's shard artifacts, merges, binds, and uploads the lane envelope. Linux and macOS keep the single complete job. `required` needs documentation, both Windows jobs, and the Linux/macOS job, and passes only when all four succeed and four lanes validate.
- Nightly triage (`regression-triage-report.mjs`, `propose-regression-fix.mjs`) reads the shard from the result or the artifact/job name, maps failed owners to the canonical Windows lane with the shard named (`windows-2025-node24 (package shard)`), and matches the shard's own job log. A failed collector job is reported as orchestration only when none of that runtime's shards failed. More than one startup evidence file for one lane throws instead of choosing one.
- `docs/validation.md` documents the shard layout, the command, the fail-closed merge, and triage mapping.
