# Design: SSH machines in A1

## Context and boundaries

Bare `a1` already uses a native attach client, a resident server, and one independent terminal holder per tab. An agent child reports structured status through its bridge; the holder retains the screen while no viewer is present. `a1 solo` and `a1 pi` are direct sessions and stay out of scope. The existing local endpoint, its owner-only credentials, and its native process identities are not remotely reachable just because a socket is forwarded. `D:/Git/herdr` demonstrates saved SSH profiles, background status, reconnect and stale-state presentation; A1 retains its own holder/server and status authority. `D:/Backups/pi/v2/sidebar/view.ts` demonstrates a three-cell collapsed chevron on the strip row, a left push sidebar, bounded geometry, mouse hit regions and context menus. Its TypeScript daemon or extension is not a suitable A1 resident-host implementation.

The user explicitly selected a **single management route**: `/workbox` in the agent menu always opens the local machine manager, never switches to a named machine. First use offers Add; later uses offer Edit or Add. Right-click Add on the Machines heading and Edit on a saved machine open the same corresponding route states. Selection of a machine or its agent in the sidebar is the only machine-switch gesture. Do not generate slash commands for saved labels.

## UX decisions

1. **One dialog family.** Use the existing A1 owned selection/line-input/stepped-dialog visual grammar, navigation, theme and hint conventions. The Add flow selects an SSH-config alias or manually entered target (no LAN scanning), checks SSH and the remote A1 package/host compatibility, edits a suggested name, then edits a remote directory suggested as that SSH user's home. Validate folder existence and access on the remote before saving; the browser/selector, if provided, lists only remote directories through bounded read-only requests. Never turn a local pathname into a remote pathname. Edit starts at the saved values and commits changes atomically; Cancel retains the old profile. Missing A1 or interactive SSH-auth/host-key requirements remain inline dialog problems with a clear normal-install or SSH remedy, never a prompt for SSH secrets inside A1. A setup dialog is the one intentional modal; there are no ancillary connection toasts or banners inside tab content.
2. **Client-local ownership.** The machine catalog, manager state and SSH credentials belong to the local client/user, not to whichever remote tab is viewed. `/workbox` requested from a remote child must route a narrowly typed command to that client's local manager; never run setup against the remote machine's own machine catalog, never parse an arbitrary terminal command out of PTY bytes, and never let an earlier request open a dialog on a different controller after transfer. Reuse an existing owned route/component when process placement permits. The implementation design must resolve how that route is presented by the foreground attach client without moving renderer or terminal-byte authority into Node or adding a second UI toolkit. If an exact code reuse is impossible across the process boundary, adapt the established owned dialog's appearance and interactions in the attach-owned chrome, rather than inventing a distinct presentation.
3. **One chevron, one strip.** With no saved machine, bare A1's current strip is unchanged. Once at least one machine is saved, the tab-strip row starts with a closed `›` control; clicking opens a left `‹` panel that pushes, rather than covers, the selected child surface. Collapse restores full width. The panel shows Local and saved machine rows with nested tab/agent rows; machines may be collapsed independently without changing selection. The selected machine's existing tabs alone occupy the strip and keep the existing `+`, context menu, shortcut and Settings semantics. Use fixed bounded width with a narrow-terminal fallback and grapheme-safe clipping; child sizing, mouse row/column mapping and clipboard remain correct. No second strip, extra status row, permanent empty rail or sidebar settings suite.
4. **Context menu, not competing commands.** Right-click on Machines offers Add. Right-click a saved machine offers Edit, Reconnect when applicable, Disable/Enable, and Forget. A disabled entry stays visible so it can be enabled via its menu. Forget removes only the local profile and SSH bridge; neither Forget nor Disable stops a remote tab/server. A keyboard context-menu action reaches the same menu, with Escape/click-away cancellation and no hidden mutation. Machine operations do not add in-agent tab notices. The user can always select Local without waiting on an SSH acknowledgement.
5. **Remote tab creation.** `+ Agent` on a remote selected machine starts a tab on that machine in the saved *remote* default directory, with the remote home suggested on setup. `+ Agent` on Local keeps A1's existing launch-cwd behavior. Changing the default affects later creations only; existing tabs keep their cwd. Remote tab IDs and session filenames are scoped by stable machine ID. No local path translation or implicit repository clone occurs.
6. **Honest statuses and selection.** Only a fresh authenticated status snapshot may show a live status. A disconnect freezes the last complete surface and rows as visibly stale (or shows no screen if the client has no cached surface), disables input and mutation on that machine, and schedules bounded reconnect. It must not silently select another machine or misreport an old `working`/`needs-input` as current. Each machine reconnects independently, with health probing and bounded backoff. Hidden machines exchange status/topology only; only the viewed machine streams the selected screen. On reconnect, verify the remote host's generation and tab identities and receive a fresh coherent surface before enabling input. Completion badges retain existing A1 bridge semantics; a new client must not claim an unseen completion it cannot prove.

## SSH and safety design

- Profiles store a stable opaque ID, user-editable label, OpenSSH target, resolved remote directory and enabled state in owner-private client state. They never store passwords, keys, host-key exceptions, PTY screens or resident tokens. OpenSSH owns authentication, SSH config and host-key verification. Plain `ssh <target>` must work before background attach can be relied on; setup can guide the user but cannot bypass a host-key mismatch or ask for secrets in a tab.
- The bridge is launched through ordinary SSH to a fixed remote A1 entry. On the remote it connects as the SSH user to that user's existing authenticated resident endpoint and forwards framed, version-negotiated client traffic; it never publishes that endpoint on a listening network port. A1 must verify the remote package, server capability and target platform before mutating anything. Existing compatible servers are kept running across client-version differences; a missing/incompatible server is an Attention state, not authority to kill or upgrade remote agents. Background reconnect does not install A1 or send remote shell-supplied arbitrary commands.
- Only the selected machine may receive input, resize, creation or controller-claim messages. Switching is target/generation-fenced; the previous machine loses control and only a fresh selected-machine frame establishes input readiness. Avoid relaying terminal bytes through JavaScript, restarting agents on disconnect, or weakening per-tab process isolation. Remote login/session policies (including Linux `KillUserProcesses`) can terminate processes on logout; report a concrete unsupported-survival reason rather than claiming persistence. Remote power loss ends processes; saved sessions can still be resumed through their existing mechanisms without automatic replay.
- Connection and setup errors must be diagnosable without printing sensitive terminal content or secrets. Authentication/host-key/unsupported-version conditions are shown in the invoked manager dialog or via the selected machine's sidebar status/context menu; no below-tab notice, toast, child banner, or misleading cached status. A failed remote action is not retried when it may already have changed state.

## Implementation sequencing (after separate maintainer approval)

1. Specify and prove a bounded SSH setup/bridge handshake, catalog authority, protocol compatibility and remote-input fencing against local and remote server snapshots. Use temporary isolated accounts/fixtures; no installation/restart during reconnect.
2. Wire the client-local `/workbox` route and machine manager to existing A1 selection, input and dialog layout primitives; verify from both Local and viewed remote tabs that it always edits the local catalog.
3. Integrate the v2-style chevron and machine list into the native attach strip with correct terminal geometry and the existing per-machine tab UX. Make right-click machine menus call the same manager states.
4. Add independent health/reconnect, stale-screen handling and remote-tab creation; verify client close/power-off simulation, SSH drop, other-machine isolation, controller races and Windows/Linux/macOS packaging. Report physical survival evidence separately when available; manual validation does not gate implementation completion.

## Risks and explicit exclusions

- The owned dialog components currently render in the agent child, while the attach client owns top-level chrome. A command invoked in a remote child cannot simply open that remote child's Settings-like route and manage the local client's files. The client-local UI bridge and reuse boundary are a first-class implementation outcome, not a claim that an existing component can be imported into Rust unchanged.
- SSH config may include globs, patterns, aliases requiring authentication, and Windows-specific paths. Setup lists only safe concrete candidates, always permits manual entry, validates the exact resolved target remotely, and never assumes a LAN host inventory.
- Narrow terminals and mouse/focus changes must not break the owned editor or Pi extension UI; sidebar collapse never modifies underlying session data.
- No LAN discovery, local/remote project synchronization, remote A1 installer, arbitrary CLI tab hosting, cross-user access, automatic reboot resume, or change to `a1 solo`/`a1 pi`.
