## Context

Two scheduled workflows validate `develop` every night: `full-regression.yml` runs every owner on four lanes and uploads `full-regression-<sha>-<run>-<attempt>-<os>-node<n>` artifacts holding `full-regression.json` (per-owner `id`, `exitCode`, `durationMs`, `scopes`), the phase `.jsonl` records, and receipts; `release.yml` runs the same complete validation before publication. Neither records failing test names in structured evidence: the vitest default reporter writes them to the job log only, and `createValidationPhaseRecorder` deliberately records no command output. `pi-upstream-sync.yml` with `propose-pi-upgrade.mjs` and the pure `pi-upgrade-report.mjs` is the existing shape for a nightly job that pushes a branch and opens or refreshes a draft pull request with the archive App identity.

## Decisions

- **Trigger:** `workflow_run` on `workflows: [Full regression, Release]`, `types: [completed]`, gated in the job by `conclusion == 'failure'` and, for `Release`, `event == 'schedule'` so manual publication requests never open triage. Manual `Full regression` dispatches do trigger triage, because the runbook uses them for pre-merge risk checks and a failure there is the same evidence. A `workflow_dispatch` input takes a run id for reruns and dry runs.
- **Evidence sources, in order of trust:** the uploaded `full-regression.json` per lane is authoritative for which owners failed; owner ids map to `tests` in `config/integration-owners.json`; `gh run view <id> --log-failed` supplies the excerpt, filtered to vitest `FAIL`, `×`, `AssertionError`, `Error:`, and `expected`/`received` lines, bounded to 40 lines per owner and 2 KiB, so a body never carries a whole log. When a lane failed before producing `full-regression.json` (install, pack, or Defender step), the failed job name and its last bounded log lines are the evidence and the owner list is `orchestration`.
- **Suspect commits:** the last successful run of the same workflow on `develop` (`gh run list --workflow <file> --branch develop --status success --limit 1 --json headSha`) bounds `git log --first-parent <lastGreen>..<head>`; each commit is listed with its pull-request number. No success in the retained window lists the head only and says so.
- **Dedupe key:** sorted failed owner ids plus the workflow name, stored in the body fence as `"triage": {"key": "...", "runs": [...]}` next to the existing `openspec-implementation` link. An open pull request whose branch matches `fix/nightly-regression-*` and whose key equals the new one is refreshed: the new run's evidence is appended under `## Implementation` and to the change's `tasks.md` evidence list; the branch is not force-pushed. A different key opens a new pull request; the older one stays open for the maintainer.
- **Branch and scaffold:** `fix/nightly-regression-<yyyy-mm-dd>` from `origin/develop` at the failed head, one commit `chore(regression): propose the fix for the <date> nightly failure` adding only `openspec/changes/fix-nightly-regression-<date>/` (`.openspec.yaml`, `proposal.md`, `design.md`, `tasks.md`). The proposal restates the evidence in prose; tasks are unchecked `1.x` reproduce/fix/prove items so the maintainer's implementation continues in the same pull request without reshaping it. No spec delta is scaffolded.
- **Authority:** contents and pull-requests write with the App token; `develop` is read only; the pull request is created with `--draft` and never marked ready. The workflow is listed in `config/github-repository-governance.json` with a new `nightly-regression-triage` authority recognised by `inspectWorkflowSource` when the source contains `propose-regression-fix.mjs` and `--draft`.
- **Failure of the triage itself** (artifact missing, `gh` error, push rejected) fails the triage workflow with the reason in its summary and never retries the nightly; the email the maintainer already receives remains.

## Risks / Trade-offs

- Log-excerpt filtering is heuristic; a failure with an unusual reporter line shape yields a thin excerpt. The owner and test-file lists remain authoritative and the run link is always present, so the excerpt is a convenience rather than the evidence of record.
- A persistent failure that recurs nightly is refreshed on the same pull request rather than piling up candidates; a flaky owner that fails on alternating nights therefore produces one candidate whose evidence list shows the pattern.
- The scaffolded change without a delta relies on the finalization path accepting a skipped `specs` artifact; task 3.4 proves that on a real draft before the change is accepted.
