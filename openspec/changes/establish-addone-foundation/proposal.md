## Why

The v2 prototype proves the value of a multi-agent terminal workspace, but its UI and agent lifecycle are embedded in Pi through private TUI bridges, process-global reload state, and exact-version host profiles. AddOne needs an independent, cross-platform terminal-host architecture that preserves the strongest v2 UX and makes fullscreen Native Pi observably indistinguishable from direct execution after handoff, while allowing AddOne and Pi upgrades, worker restarts, third-party Pi extensions, and non-Pi terminal agents without leaking child protocols into the parent terminal or putting the user in the critical path for regression detection.

## What Changes

- Introduce AddOne as a standalone terminal application that owns its complete shell, including workspaces, tabs, sidebar, structured conversation views, terminal views, input routing, drafts, status, and notifications.
- Deliver the first user-visible walking skeleton through the production boundaries: running `addone` immediately launches vanilla Native Pi in a supervisor-owned PTY with no AddOne intro or startup frame and gives that PTY the complete terminal viewport with no tabs, `+` control, sidebar, status line, or other AddOne chrome.
- Introduce a persistent supervisor that owns durable logical-agent identity, process generations, workspace state, session references, leases, recovery, and communication with disposable UI clients.
- Introduce a minimal AddOne bootstrap and immutable, content-identified AddOne release cohorts so an npm update cannot connect a newly installed UI to an incompatible supervisor or require manual PID discovery and termination. Candidate activation drains or defers busy generations, automatically reconciles stale ownership, and keeps every live UI/supervisor cohort on one recorded release.
- Replace a manually incremented global protocol-version constant with negotiation of required control-envelope features and generated contract identity; incompatible peers fail before commands are accepted and are reconciled by the bootstrap rather than exposed as `invalid client message` failures.
- Introduce a capability-based agent-driver boundary so the UI and supervisor do not depend on Pi-specific or PTY-specific APIs.
- Introduce a Managed Pi driver that runs an exactly pinned Pi runtime through its documented RPC interface and maps Pi messages, tools, sessions, queues, retries, compaction, and portable extension UI requests into AddOne events.
- Introduce one application-agnostic cross-platform terminal-session and rendering pipeline for Native Pi, Claude Code, Codex, interactive shells, and arbitrary commands. Child output remains semantically opaque and terminates in an AddOne-owned virtual terminal, while generic terminal render transactions preserve native-feeling frame boundaries, scrolling, cursor behavior, input latency, and backpressure without inspecting an executable name, argument vector, or visible content. Shell-backed sessions can run later CLIs without adding a PTY for each command.
- Support later reproduction of the v2 tab strip, workspace sidebar, status presentation, structured transcript, and terminal-emulation UX through AddOne-owned models and components. The behavioral oracle for that later work SHALL be an exactly identified Pi runtime launched with the v2 extension profile enabled and exercised directly and through AddOne's PTY simulation; historical screenshots are supplemental diagnostics, not a required or normative baseline.
- Persist AddOne control-plane state independently from Pi JSONL sessions using Node's built-in SQLite API and enforce one live writer for each resumable session.
- Install Pi runtimes and extension profiles side by side so candidate updates can be tested before promotion and older agents can continue using their existing runtime.
- Establish hermetic driver, PTY, recovery, update-transition, compatibility, dependency-policy, and regression-test foundations. Every confirmed production, manual-validation, or release-gate regression becomes retained evidence plus a deterministic failing simulation before its correction is considered complete; every bug fix runs affected-boundary and neighboring simulations under production defaults before broad gates, every added or modified test is actually run and passes both focused and containing build/gate validation before completion or commit, and the passing regressions remain in the appropriate mandatory gate so users never need to request coverage or test execution separately. Publication packs first, installs and launches the exact immutable tarball under production defaults, and uploads only that certified artifact. Provide a first-class development-preview release channel in which `npm run publish:next` creates the next immutable `-dev.N` package, validates and publishes that exact artifact under npm `next`, and the installed `addone`/`a1` updater selects either stable npm `latest` through `update` or preview npm `next` through `update:next`. Both commands perform the same immediate stop-install-activate transaction; invocation is explicit consent to terminate all verified AddOne-owned UI, supervisor, and non-resumable child sessions. Each SHALL activate the exact installed target without requiring a separate status, shutdown, restart flag, PID command, or state-directory deletion. A separate read-only `version` command SHALL report the locally installed package version together with npm stable `latest` as `Release` and npm preview `next` as `Next`, without starting AddOne runtime processes. Before any later product feature proceeds, a generic multi-CLI direct-versus-AddOne gate SHALL reject extra visible frames, transport-chunk repainting, generated-text or fixed-row flicker, input latency, irregular frame cadence, output amplification, and host-output backpressure failures. Pi is one mandatory demanding workload in that corpus, not a source of terminal-core patches. AddOne's production, development, build, test, and optional dependency graph contains no package marked deprecated. Release gates compare direct and AddOne-hosted fullscreen Pi from physical host input through child effects and restored parent-shell behavior on Windows 11, current Ubuntu LTS, and current/previous macOS. Deterministic fixtures remain transport oracles, while packaged candidates launch an exactly identified vanilla Pi default interactive TUI without user extensions, model access, or network access and prove recognizable readiness, rendering, keyboard, physical-wheel-equivalent mouse routing, paste, native dialogs, resize, repeated-Ctrl+C exit, and usable parent-terminal restoration. An N−1 release-cohort scenario proves that updating with a live old supervisor never exposes a protocol error or requires manual process termination; later gates add the separately pinned v2 extension profile and an independent evaluator-agent path.
- **BREAKING** Replace the implemented raw child-output handoff with a terminal-multiplexer boundary: the foreground AddOne client exclusively owns physical-terminal modes, the supervisor owns resident virtual terminal state, and no child alternate-screen, mouse, keyboard, paste, cursor, or Win32 input-mode control sequence is written directly to the host.
- Explicitly exclude private Pi host bridges, TUI prototype patching, whole-system `/reload` fanout, daemon hot-code swapping, process-global reload-survival state, and transparent child-control-sequence relay from the new architecture.
- Defer tabs, the `+` control, sidebar, status chrome, and all AddOne shortcuts from the first fullscreen Native Pi iteration while retaining them as later milestones in this change. Remove the launch intro from this baseline. Also defer full migration of Git, plans, answer/refinement flows, advanced paste/chips, modes, outro animation, and complete v2 visual parity to follow-up changes.

## Capabilities

### New Capabilities
- `addone-shell`: Standalone AddOne bootstrap and immediate command startup, immutable release selection, exclusive outer-terminal ownership, initial automatic vanilla Pi default-interaction presentation over AddOne's complete viewport with no AddOne startup frame, exact native closure spacing, and later workspace, tab, add-control, sidebar, structured-conversation, input-routing, draft, status, and notification behavior.
- `agent-supervision`: Durable logical-agent and workspace lifecycle, co-versioned process cohorts, negotiated control contracts, safe candidate activation, automatic stale-process reconciliation, generations, leases, UI reconnection, recovery, and capability-aware driver coordination.
- `managed-pi-runtime`: Managed Pi RPC execution, session continuity, normalized events, pinned runtimes, extension profiles, and portable Pi extension interaction.
- `terminal-agent-runtime`: Cross-platform virtual terminal sessions for Native Pi, shells, and other command-line agents, including isolated child protocols, native-equivalent cells and behavior, semantic host-input decoding, child-mode-aware input encoding, terminal responses, mouse/scroll routing, flicker-free rendering, resize, exact host restoration, and driver-specific resume capabilities.
- `isolated-regression-testing`: Hermetic scenario execution, packaged-candidate and N−1 update-transition validation, cross-platform direct-versus-hosted parity with deterministic fixtures and exactly identified real Pi runtimes, physical-wheel-equivalent input, readiness/color/input/dialog/mouse/resize/flicker assertions, functional post-exit parent-shell probes, compatibility matrices, PTY artifacts, and evaluator-agent regression inspection.

### Modified Capabilities

None. This proposal establishes the first AddOne capabilities; no main specifications currently exist.

## Impact

- Creates a new standalone AddOne application and supervisor rather than extending the v2 Pi-hosted runtime in place.
- Establishes negotiated AddOne control contracts between the UI, supervisor, and agent drivers from the first Native Pi walking skeleton rather than introducing a temporary UI-owned worker path; the initial UI is nevertheless a chrome-free, single-session terminal-host projection so direct-observable Pi parity can be validated before AddOne navigation is layered over it.
- Changes AddOne self-update from in-place replacement of files used by persistent processes to immutable release materialization, package-derived release identity, deferred or drained cohort activation, and automatic stale-owner recovery behind a minimal bootstrap.
- Adds controlled dependencies on a pinned outer TUI toolkit, Node's built-in `node:sqlite` transactional control store, Pi RPC worker distributions, PTY/terminal-emulation libraries, and platform host-input adapters; direct and transitive AddOne-owned dependencies marked deprecated are release-blocking.
- Uses executable v2 extension behavior under an exactly identified Pi runtime as the later UX oracle while selectively reproducing pure models, rendering calculations, PTY knowledge, and tests. Archived screenshots may aid diagnosis but do not block the vanilla fullscreen release and are not treated as normative evidence.
- Restricts Pi package imports to Pi driver/adapter boundaries, PTY dependencies to terminal-driver boundaries, and platform console APIs to host-terminal adapters. Herdr is architectural prior art only; its AGPL implementation is not copied into AddOne.
- Changes the future update model from in-process reload fanout to idle drain, process replacement, exact-session verification, candidate certification, and rollback.
