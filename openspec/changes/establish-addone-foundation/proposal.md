## Why

The v2 prototype proves the value of a multi-agent terminal workspace, but its UI and lifecycle are coupled to private Pi host infrastructure. The first standalone AddOne terminal pipeline has also proven architecturally unfit for production: duplicated terminal parsing, mode tracking, input translation, frame inference, cell reconstruction, and host-origin compensation still produce rendering artifacts, input inconsistencies, and added latency despite passing self-modelled simulations. AddOne now needs a simpler native-parity baseline and a separately justified composition architecture before later product work can continue.

## What Changes

- Introduce AddOne as a standalone terminal-based application on Windows, macOS, and Linux that owns its complete shell, including workspaces, tabs, sidebar, structured conversation views, terminal views, input routing, drafts, status, and notifications. AddOne SHALL remain inside the user's native terminal environment rather than replacing it with a browser or desktop GUI.
- Deliver the first production-ready user-visible baseline through a transparent full-viewport terminal capability: running `addone` immediately launches vanilla Native Pi with no AddOne intro, startup frame, chrome, input translation, framebuffer reconstruction, or inferred render scheduling. Prefer direct attachment to the physical terminal; evaluate raw PTY relay only if required lifecycle ownership cannot be achieved by direct attachment and physical-host parity proves that the relay adds no observable difference.
- Introduce a persistent supervisor that owns durable logical-agent identity, process generations, workspace state, session references, leases, recovery, and communication with disposable UI clients.
- Introduce a minimal AddOne bootstrap and immutable, content-identified AddOne release cohorts so an npm update cannot connect a newly installed UI to an incompatible supervisor or require manual PID discovery and termination. Candidate activation drains or defers busy generations, automatically reconciles stale ownership, and keeps every live UI/supervisor cohort on one recorded release.
- Replace a manually incremented global protocol-version constant with negotiation of required control-envelope features and generated contract identity; incompatible peers fail before commands are accepted and are reconciled by the bootstrap rather than exposed as `invalid client message` failures.
- Introduce a capability-based agent-driver boundary so the UI and supervisor do not depend on Pi-specific or PTY-specific APIs.
- Introduce a Managed Pi driver that runs an exactly pinned Pi runtime through its documented RPC interface and maps Pi messages, tools, sessions, queues, retries, compaction, and portable extension UI requests into AddOne events.
- Introduce two explicit, capability-negotiated terminal modes instead of forcing every workload through one pipeline. Transparent sessions prioritize direct native-terminal behavior and latency but do not promise resident surfaces, reconnection, panes, or composition. Composed sessions provide those features only through one authoritative mature terminal core that owns PTY integration, parsing, modes, input encoding, terminal responses, screen/scrollback, and operation/damage reporting as one coherent boundary. Both modes SHALL be application-agnostic and cross-platform: Pi, shells, editors, pagers, multiplexers, and unrelated interactive/fullscreen CLIs receive no executable-, argument-, or content-specific rendering or input workaround.
- Support later reproduction of the v2 tab strip, workspace sidebar, status presentation, structured transcript, and terminal UX through AddOne-owned models and components. The behavioral oracle for that later work SHALL be an exactly identified Pi runtime launched with the v2 extension profile enabled and exercised through independently observed native execution plus any separately certified composed capability; the retired AddOne PTY simulator and historical screenshots are supplemental history, not normative acceptance baselines.
- Persist AddOne control-plane state independently from Pi JSONL sessions using Node's built-in SQLite API and enforce one live writer for each resumable session.
- Install Pi runtimes and extension profiles side by side so candidate updates can be tested before promotion and older agents can continue using their existing runtime.
- Establish hermetic driver, lifecycle, update-transition, compatibility, dependency-policy, and regression-test foundations. Rendering and input acceptance SHALL come from independent physical-host observations and packaged direct-versus-AddOne comparisons, not from a test encoder, mode oracle, framebuffer simulator, or terminal model duplicating production assumptions. Exact-artifact publication, stable/preview update transactions, dependency policy, and architecture-independent lifecycle gates remain mandatory.
- **BREAKING** Freeze and remove the current production terminal-emulation pipeline before implementing its replacement. Delete its regex mode tracker and query interception, custom Win32/Kitty/modifyOtherKeys translation, framebuffer-derived scroll inference, cadence-derived frame guessing, startup-row compensation, manual cell/style VT reconstruction, ConPTY fallback branches, and associated protocol/rendering glue rather than wrapping them in another layer.
- **BREAKING** Remove simulations, rendering tests, custom-input tests, and regression tests whose assertions encode the retired pipeline or reproduce its own assumptions. Retain architecture-independent domain, storage, release, update, protocol, and true integration coverage; preserve historical failures as non-executable evidence; then build replacement terminal tests from first principles against independent host behavior.
- Explicitly exclude private Pi host bridges, TUI prototype patching, whole-system `/reload` fanout, daemon hot-code swapping, process-global reload-survival state, and any new application-specific terminal patch. Transparent child-terminal attachment is an intentional capability, not a hidden executable-name exception.
- Defer tabs, the `+` control, sidebar, status chrome, and all AddOne shortcuts from the first fullscreen Native Pi iteration while retaining them as later milestones in this change. Remove the launch intro from this baseline. Also defer full migration of Git, plans, answer/refinement flows, advanced paste/chips, modes, outro animation, and complete v2 visual parity to follow-up changes.

## Capabilities

### New Capabilities
- `addone-shell`: Standalone AddOne bootstrap and immediate command startup, immutable release selection, transparent full-viewport Native Pi handoff with no AddOne startup frame or translation, exact native closure behavior, and later AddOne-owned workspace surfaces.
- `agent-supervision`: Durable logical-agent and workspace lifecycle, co-versioned process cohorts, negotiated control contracts, safe activation, generations, leases, and explicit foreground-terminal ownership whose reconnect/recovery promises depend on terminal capability.
- `managed-pi-runtime`: Managed Pi RPC execution, session continuity, normalized events, pinned runtimes, extension profiles, and portable Pi extension interaction.
- `terminal-agent-runtime`: Separate transparent and composed terminal capabilities for arbitrary terminal applications on Windows, macOS, and Linux. Transparent mode delegates behavior to the native physical terminal for direct parity; composed mode uses one authoritative mature cross-platform terminal core, remains application-agnostic, and advertises only the behavior it can certify without per-application hacks.
- `isolated-regression-testing`: Hermetic lifecycle scenarios, exact packaged-candidate and update-transition validation, independent physical-host input/rendering oracles, cross-platform direct-versus-hosted real-runtime comparison, capability-specific verdicts, retained artifacts, and evaluator inspection without self-modelled terminal simulations as acceptance evidence.

### Modified Capabilities

None. This proposal establishes the first AddOne capabilities; no main specifications currently exist.

## Impact

- Creates a new standalone cross-platform terminal application and supervisor rather than extending the v2 Pi-hosted runtime in place or replacing terminal interaction with a GUI/web shell.
- Establishes negotiated AddOne control contracts between bootstrap, UI, supervisor, and drivers while allowing the initial chrome-free foreground terminal broker to attach Native Pi transparently instead of serializing input and reconstructed frames through the control protocol.
- Changes AddOne self-update from in-place replacement of files used by persistent processes to immutable release materialization, package-derived release identity, deferred or drained cohort activation, and automatic stale-owner recovery behind a minimal bootstrap.
- Removes the current `@xterm/headless`-plus-custom-terminal production path and its invalid architecture-specific tests before selecting a replacement. The composed-mode spike evaluates the MIT-licensed WezTerm Rust stack first through a minimal batched native boundary, with libvterm and a public-API-only xterm.js design as ordered fallbacks. Any selected native stack requires pinned source identity, reproducible Windows/Linux/macOS builds, package integrity, licensing review, and no deprecated AddOne-owned dependencies.
- Uses executable v2 extension behavior under an exactly identified Pi runtime as the later UX oracle while selectively reproducing pure models, rendering calculations, PTY knowledge, and tests. Archived screenshots may aid diagnosis but do not block the vanilla fullscreen release and are not treated as normative evidence.
- Restricts Pi package imports to Pi driver/adapter boundaries and platform/native terminal dependencies to explicit terminal boundaries. Herdr remains architectural prior art only; its AGPL implementation is not copied into AddOne.
- Changes the future update model from in-process reload fanout to idle drain, process replacement, exact-session verification, candidate certification, and rollback.
